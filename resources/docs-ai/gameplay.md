# Agent Instructions: Gameplay Mechanics Implementation

This document outlines the architectural and technical requirements for implementing player traversal (double jump, wall climb), combat (close-combat strike, ammo-gated shooting, dagger pickups, coin pickups, chest interaction), and enemy patrol movement using Ashley ECS in libGDX.

---

## 1. State Management & Components

### A. Extended PlayerComponent
Track the advanced state variables required for these mechanics directly inside the `PlayerComponent`:
*   `int jumpCount` (Tracks current jumps executed; resets to 0 when grounded).
*   `int maxJumps = 2` (Allows for double jumping).
*   `boolean isWallClimbing` (Flag for wall attachment).
*   `int facingDirection` (-1 for left, 1 for right).
*   `int ammo` / `int maxAmmo = 30` (Dagger/shoot ammo count and cap; the HUD's item tracker displays this as `x NN/30`). A fresh game starts the player with `PlayerConfig.START_BULLETS` ammo (default `0`), set by `PlayerFactory.createPlayer(...)`; a loaded save overrides it via `SaveData.applyTo(...)`.
*   `int coins` (Currency spent in the Shop/Upgrade mechanic — see §2.O).
*   `int swordDamage = 5` (Melee damage per hit, read dynamically by `MeleeAttackSystem` on every strike; raised to `8` by the "Sharp Edge" shop upgrade — see §2.O).
*   `boolean sharpEdgePurchased`, `boolean daggerBandolierPurchased`, `int ironHeartCount` (One-time-purchase flags and repeat-purchase counter for the three shop upgrades — see §2.O).
*   `Timer shootCooldown` (Prevents ranged-shot spamming, independent of melee).
*   `Timer meleeCooldown` (Prevents melee-strike spamming, independent of shooting).
*   `Timer meleeAttack` (Counts down while the melee strike hitbox is active; active means a strike is in progress).
 *   `boolean meleeHasHit` (True once a swing has landed at least one hit — enemy damaged, chest opened, secret wall broken, or wall clank; gates the one-shot secret-wall break / wall-clank effects, see §2.C.4).
 *   `ObjectSet<Entity> meleeHitEnemies` (Enemies already damaged by the current swing; cleared at every swing start by `PlayerInputSystem` alongside `meleeHasHit`, so a swing hits every enemy that comes into reach as the blade extends but never the same enemy twice — see §2.C.4).
*   `Timer hitInvulnerability` (Grace period after being hit by an enemy; while active, further enemy contact does not reduce health again — see §2.J).
*   `Timer hurtTimer` (Short hit-stun window started alongside `hitInvulnerability` on every hit, long enough to play the `HURT` animation once; while active, movement/jump/melee/shoot input is locked and the hurt pose is shown — see §2.J).
*   `boolean interactPressed` (One-shot: true only during the frame the interact key/touch button was pressed; see §2.M).
*   `boolean nearExit` (True while inside any exit gate's proximity sensor; drives the touch UI prompt — see §2.M).
*   `boolean dropRequested` (One-shot: true only during the frame the drop-through-platform key/touch button was pressed; starts `dropWindow` — see §2.W).
*   `boolean onDropTile` (True while the player is grounded on top of a one-way platform tile; drives the contextual `v` touch button — see §2.W).
*   `Timer dropWindow` (Short pass-through window, ~`0.25s`; while active, `MovementSystem` lets the player fall through one-way platforms — see §2.W).
*   `int healingPotions`, `int strengthPotions`, `int speedPotions`, `int invulnerabilityPotions` (Held potion counts, each capped at `GameConstants.POTION_CAP`; filled by `PickupSystem` from `potion` object-layer markers — see §2.E.1).
*   `PotionType selectedPotion` (The potion type the "use potion" action currently targets, cycled by `Z` — see §2.E.1).
*   `Timer potionCooldown` (Short drink-spam window, `GameConstants.POTION_USE_COOLDOWN`; started on every successful drink — see §2.E.1).
*   `boolean inAir` + `float maxAirHeight` (Airborne tracking used to gate **landing dust** — see §2.B.4: `inAir` is true from the frame the player leaves the ground until the next grounded frame, and `maxAirHeight` records the highest feet position reached while airborne, so a landing puff fires only when the fall exceeded one tile).
*   `boolean squashActive`, `boolean squashIsStretch`, `float squashAmount`, `float squashBaseX`, `float squashBaseY` (Landing **squash-and-stretch** visual pulse — see §2.B.4: `SquashSystem` captures the resting scale into `squashBaseX/Y`, applies a flatter/wider deviation from `squashAmount` that exponentially decays to zero each frame, and snaps back exactly when the pulse ends. Jump *stretch* was removed for feel; `squashIsStretch` is retained unused. **Currently disabled by default** — the trigger is gated on `FeatureFlags.isSquashEnabled()` (persisted pref, default `false`) until the look is finalized.)

All of the countdown fields above (`shootCooldown`, `meleeCooldown`, `meleeAttack`, `hitInvulnerability`, `hurtTimer`, `dropWindow`, `potionCooldown`) are instances of the reusable `com.axehigh.platformer.util.Timer` helper (`start()`/`update()`/`isActive()`/`isDone()`), not raw `float`s; use it for any new cooldown/countdown/grace-period field instead of hand-rolling a decrement. The buff countdowns (`strength`, `speed`, `invulnerability`) live on `BuffComponent`, and the enemy attack countdowns (`attackCooldown`, `windUp`) live on `EnemyAttackComponent` — all follow the same helper — see §2.E.1.

### B. BulletComponent (New)
Applied to spawned projectile entities:
*   `float damage`
*   `float lifetime` (Despawns the bullet after a set time if it doesn't hit anything).

### C. DaggerPickupComponent (New)
Marker component applied to object-layer pickup entities that replenish shoot ammo:
*   `int amount = 5` (Ammo granted to `PlayerComponent.items` on pickup, capped at `maxAmmo`).

### D. CoinPickupComponent (New)
Marker component applied to coin pickup entities:
*   `int amount = 1` (Coins granted to `PlayerComponent.coins` on pickup, uncapped; the HUD's existing coin counter reflects this immediately).

### D.1. PotionPickupComponent (New)
Marker component applied to potion pickup entities (spawned from `"potion"` object-layer markers):
*   `PotionType potionType` (Which held-potion count the pickup fills — `HEALING`/`STRENGTH`/`SPEED`/`INVULNERABILITY`).
*   `int amount = 1` (Count added to the matching `PlayerComponent` held-potion field on pickup, capped at `GameConstants.POTION_CAP`; an over-cap pickup converts to `GameConstants.POTION_OVERFLOW_COINS` coins instead — see §2.E.1).

### D.2. BuffComponent (New)
Holds the player's three drink-buff timers (added to the player entity by `EntityFactory.createPlayer`):
*   `Timer strength` (`20s` via `startStrength()`; while `isActive()`, melee strikes deal `swordDamage × STRENGTH_DAMAGE_MULTIPLIER` (doubles base damage)).
*   `Timer speed` (`15s` via `startSpeed()`; while `isActive()`, `BuffSystem` scales `maxSpeedX` by `SPEED_MULTIPLIER` and sets `player.maxJumps = 3` for triple jump; `speedApplied` + `speedBaseMaxSpeedX` cache the pre-buff base so it can be re-asserted/restored, and `maxJumps` is restored to `2` on expiry).
*   `Timer invulnerability` (`10s` via `startInvulnerability()`; while `isActive()`, `PlayerDamageResolver` ignores all damage).

See §2.E.1 for the full consumption flow.

**Coin sprite:** Every coin entity — map-placed markers **and** chest/enemy-dropped pops — is an **animated entity coin** rendered from the `Coin_01`..`Coin_06` atlas regions in `gfx/origin-game.atlas` (0.1s/frame spin via the generic `AnimationSystem`), never from the Tiled tile sprite. All coins render at **half a map tile** — `DEFAULT_COIN_SIZE = 8f` scaled by `unitScale` (i.e. `8f * unitScale`, a 64px coin on 128px-tile maps) — regardless of source, so map coins and popped coins are pixel-identical. Map markers are a pure placement guide: `EntityFactory.createCoinPickup(x, y, width, height)` sizes the coin from the half-tile constant and centers it on the marker rect (marker dimensions are ignored); popped coins use the same size via `createCoinPickup(x, y)`/`createPoppedCoinPickup(...)`. Because the animation lives on the entity, map coin markers can be plain rectangles or any coin tile — the result looks identical.

### E. ChestComponent (New)
Tracks a chest entity's open state after being melee-struck:
*   `boolean opened = false`
*   `Timer disappearTimer` (Short delay (~`0.3s`) after opening before the loot pop; the chest **stays** in the world as an opened container and is never removed — see §2.F).
*   `boolean coinsDropped = false` (One-shot guard: pops the loot burst exactly once, the frame `disappearTimer` completes after opening, so an already-opened chest never drops twice).
*   `PotionType potionType = null` (If non-null, the chest drops a potion of this type instead of coins when opened. Set from the `potionType` Tiled object property on chest markers; `null` = coin-only chest — see §2.F).

### E.1. PoppedItemComponent (New)
Empty marker component applied to a pickup entity that was launched with an initial `MovementComponent.velocity` (chest- and enemy-dropped coins, see §2.F and §2.G.10). Checked by `MovementSystem`: the instant the entity's `grounded` flag first becomes `true`, its horizontal velocity is also zeroed so it comes to a dead stop exactly where it lands, instead of sliding indefinitely (there is no ground friction elsewhere in the system).

### E.2. LevelExitComponent (New)
Marks an exit-gate entity as an actual level-transition trigger (as opposed to a purely decorative gate):
*   `String nextLevelPath = ""` (Target `.tmx` asset path, e.g. `maps/demo_room.tmx`; read from the gate object's `nextLevel` custom Tiled property by `EntityFactory.createExitGate(...)`. An exit-gate object gets no `LevelExitComponent` (and is purely decorative) only when it has neither a `nextLevel` property **nor** `isFinal="true"`.)
*   `boolean isFinalLevel = false` (When true, interacting with the gate triggers the victory flow — `VictoryScreen` — instead of loading the next level. Set from the `isFinal=true` custom Tiled property on the exit-gate object. A final gate may omit `nextLevel` entirely, as on World 2's `level_10_final`.)

See §2.M for the full multi-level progression mechanic built on top of this component.

### F. Extended EnemyComponent
Adds simple back-and-forth patrol state on top of the existing `float health = 10`:
*   `float speed = 20` (Horizontal patrol speed, world units/second).
*   `int direction = 1` (Current patrol direction: `1` right, `-1` left).
*   `float patrolRange = 64` (Max distance walked away from `originX` in either direction before turning around; still applies as an optional secondary cap alongside ledge detection — see §2.G. Only used in `PATROL` mode; `SIDE_TO_SIDE` skips it.)
*   `float originX` (World-space X the enemy was spawned at, set once by `EntityFactory`; the center of its patrol path).
*   `AiMode aiMode = PATROL` (enum `PATROL`/`SIDE_TO_SIDE`; selects the patrol behavior — origin-bounded walking vs. endless walking that turns only on walls/ledges/hazards. Set per-marker from the Tiled `aiMode` property — see §2.G.11).
*   `Timer turnPause` (Brief stand-still after every turn-around — wall, ledge, hazard, or `PATROL` range limit — during which the enemy's velocity is zeroed so the direction change is visible — see §2.G.12).
*   `float originX` (World-space X the enemy was spawned at, set once by `EntityFactory`; the center of its patrol path).
*   `Timer hitStun` (Grace period after taking damage; while active, patrol AI pauses and further hits are ignored so a knockback pop can play out — see §2.I). Its duration is dynamically set to the length of the `HURT` animation (min 0.3s).
*   `Timer postHitIdle` (Brief pause after `hitStun` ends during which the enemy stays stationary in `IDLE` state before resuming patrol — see §2.I.5).
*   `boolean isDead = false` (Set to `true` when health reaches zero; triggers the death sequence — see §2.G.9).
*   `Timer deathTimer` (Tracks the death animation duration **plus** the `0.8s` post-animation blink window (`EnemyDamageResolver.DEATH_FLASH_DURATION`); once it elapses, the entity is removed from the engine. The blink starts as soon as the timer has `0.8s` or less remaining.)
*   `boolean deathCoinsSpawned = false` (Guard so the death coin drop fires exactly once, on the first frame `EnemySystem` observes the death — immediately on the kill, before the corpse lingers/flashes.)
*   `int roomIndex = -1` (Index into `RoomState.rooms` of the Room rectangle this enemy was spawned inside of, set once by `EntityFactory` from the spawn point's containment; `-1` if none. Drives the Room-Based Entity activation described in §2.N.)

See `resources/docs-ai/enemies.md` for the full enemy catalog (current type(s), stats, sprite, and how to add new enemy types) — this section only covers the shared `EnemyComponent` fields/mechanic, not per-type tuning.

### G. FlyingEnemyComponent (New)
Marker component layered on top of `EnemyComponent`, tagging an enemy as immune to gravity; checked by `MovementSystem`, which skips its gravity/wall-slide velocity-Y update entirely when present, so the entity never falls under gravity on its own. Also carries the vertical bob-wave tuning `EnemySystem` uses to give it a flapping motion (see §2.K):
*   `float bobAmplitude = 8` (World units the bob swings above/below the height it was at when patrol last resumed.)
*   `float bobFrequency = π` (Angular frequency of the bob wave, radians/second; default is roughly a 2 second period.)
*   `float bobTime = 0` (Elapsed-time accumulator driving the wave's phase; frozen while patrol AI is paused. Seeded to a **random phase** at spawn — uniform over one full bob period — so multiple flyers don't flap in unison.)

### H. EnemyShooterComponent (New)
Marker component layered on top of `EnemyComponent`:
*   `Timer shootCooldown` (Counts down between shots; once done, `EnemyShootSystem` fires and restarts it.)
*   `float shootInterval = 5` (Seconds between shots.)

See §2.L and §2.N.

### I. EnemyBulletComponent (New)
Empty marker component (`Poolable`), no fields. Tags a bullet entity as enemy-fired (as opposed to the player's own bullets), attached alongside `BulletComponent` by `EnemyShootSystem`. See §2.L.

## 2. Mechanics & Logic Breakdown

### A. Double Jump Logic (`PlayerInputSystem` & `MovementSystem`)
0.  **Jump envelope (design model).** For map/generator design, the player is modeled as a **1×1-tile box** (the real collision box is smaller: 30×40 px at 1× unitScale). Derived from the physics constants below (`JUMP_VELOCITY = 220`, `DOUBLE_JUMP_FACTOR = 0.7`, gravity `-600`, `MOVE_SPEED = 90`), the measured jump envelope is:
    *   **Single jump — up:** 2 tiles of ledge clearance (feet rise).
    *   **Single jump — across:** 4 tiles.
    *   **Double jump — up:** 3 tiles total from ground.
    *   **Double jump — across:** 7 tiles.
    Heights are **ledge clearance** (how high the feet rise), so a 2-tile jump comfortably clears a 2-tile obstacle for a 1-tile player. The map generator encodes these as `JUMP_*_*` constants and checks template courses / platform staircases stay within them (`map-design-for-tiled.md` §9).
1.  **Grounded Reset:** When the physics/collision system detects the player is standing on a solid tile, reset `jumpCount` to `0`.
2.  **Jump Trigger:** When the Jump button (**A**) is pressed:
    *   If `jumpCount < maxJumps`, allow the jump by setting the upward vertical velocity.
    *   Increment `jumpCount` by 1.
3.  **Animation State:** Trigger a distinct flipping or spinning animation frame if `jumpCount == 2`.
4.  **Jump & Landing Smoke:** A ground jump (one where `movement.grounded == true` at the moment the jump fires) spawns a one-shot smoke puff under the player via `ParticleHelper.spawnSmallSmoke(...)` (`GlobalParticles.SMOKE`, `particles/smoke/ParticleParkSmoke.p`, base scale `5.0`), driven to completion by `ParticleSystem`. The puff spawns at a **random spot under the player** — the spawn X is a uniform random offset across the collision box width (not the fixed center), so consecutive puffs are never in the exact same place. The effect's emitter duration is `500ms` (half of its original `1000ms`), so it spawns particles for ~half a second and the entity is removed once the last particle dies (`ParticleEmitter.isComplete()`), leaving the puff visible ~0.5-0.7s total. The same puff spawns again when the player **lands**, but **only when the fall exceeded one tile** (`16` world units at 1x scale, i.e. `16 × unitScale`): while airborne the player's air phase is tracked on `PlayerComponent` (`inAir` = true from the frame it leaves the ground, `maxAirHeight` = highest feet position reached), and on the landing frame `MovementSystem.onLanding(...)` (shared with `MovingPlatformSystem` so ground and platform landings are identical) spawns the puff only when `maxAirHeight − feet ≥ 16 × unitScale`. The height gate applies to **both** jump landings and ledge/drop landings — a >1-tile drop off a ledge puffs just like a jump landing — while short hops and riding a platform up spawn nothing. The landing puff's scale grows with fall impact speed (a proxy for fall duration): `5.0` for a short hop, lerping to a max of `10.0` at terminal fall speed (`GameConstants.MaxSpeedY`). The same `onLanding(...)` hook also drives the landing **squash**: on jump landings (`jumpCount > 0`) it calls `SquashSystem.trigger(player, transform, false)`, which squashes the sprite flatter/wider and decays back to its resting scale over ~`0.25s` (jump *stretch* was removed for feel) — **disabled by default** behind `FeatureFlags.isSquashEnabled()` (persisted pref, default `false`) until the look is finalized. Air/double jumps spawn no smoke; the puffs are purely visual.

### B. Wall Climbing Logic (`MovementSystem`)
1.  **Feature Flag:** The entire wall-climb mechanic is gated behind `FeatureFlags.isWallClimbingEnabled()` (default **ON**, persisted via `GamePreferences`, toggled live from the pause dialog's "Wall Climb" button). When the flag is **OFF**, `MovementSystem` never latches onto a wall: the reduced wall-slide gravity and max-fall-speed clamp are skipped (the player falls at full gravity, and a pre-existing `isWallClimbing` is cleared the same frame), and `jumpCount` is never reset to `1` by wall contact — so **no wall-jump** either. Only the plain double-jump remains. This flag is the first step towards replacing wall-climb with ladder/vine traversal (planned: `type="ladder"` Tiled objects, `LadderComponent`/`LadderSystem`, `isClimbing` state that phase-throughs solid platforms).
2.  **Wall Detection:** Perform a horizontal AABB collision check slightly ahead of the player in their `facingDirection`.
3.  **Latch Condition:** If the player is in mid-air, moving towards a solid wall tile, and holding the Directional D-Pad toward that wall (and the feature flag is ON):
    *   Set `isWallClimbing = true`.
    *   Zero out or significantly reduce downward vertical velocity (slight sliding effect).
    *   Reset `jumpCount = 1` to allow a "Wall Jump" away from the surface.
4.  **Release Condition:** Detach if the player presses the opposite direction or falls past the bottom of the wall tile.

### C. Close-Combat Strike Logic (`PlayerInputSystem` & `MeleeAttackSystem`)
1.  **Input:** Listen for the Attack button (**B**, keyboard `J` or keyboard `B`), independent of the shoot button.
2.  **Cooldown Check:** Only allow a strike if `meleeCooldown.isDone()`.
3.  **Trigger:** On a valid press, `start()` `meleeAttack` (an active window matching the `ATTACKING` animation duration), reset `meleeHasHit = false`, and `start()` `meleeCooldown` (set to at least the animation duration to ensure it finishes) — no ammo is consumed and no projectile entity is spawned.
4.  **Hit Resolution (`MeleeAttackSystem`):** While `meleeAttack.isActive()`, build a strike rectangle offset from the player's `CollisionComponent` bounds in `facingDirection`, with the horizontal reach taken from the sprite's **per-frame reach table** (`PLAYER_ATTACK_REACH` in `PlayerConfig`, the central tuning class for the player's melee/ranged combat stats (swing cadence, hitbox shape, bullet tuning), scaled by the hero sprite's `PlayerScale` — see §2.T): the `ATTACKING` animation frame is derived from the swing's elapsed time, and each frame maps to a reach (index 0 = windup/recovery, `0` = cannot hit), so a swing only registers while the blade is actually extended. Each attacking sprite defines its own `*_ATTACK_REACH` table in `SpriteConstants` (the per-sprite geometry class), so future sprites with different attack animations get their own reach without touching `MeleeAttackSystem`. Apply melee damage read dynamically from `player.swordDamage` (base `5`, or `8` once the "Sharp Edge" shop upgrade is purchased — see §2.O; while the **Strength potion** buff is active `MeleeAttackSystem` doubles `player.swordDamage` — see §2.E.1) to **every** overlapping enemy entity, each at most once per swing (tracked in a per-swing `meleeHitEnemies` set on `PlayerComponent`, cleared at every swing start by `PlayerInputSystem` — so a swing also hits enemies that only come into reach on a later frame as the blade extends, and never re-damages the same enemy regardless of swing length vs. the `0.3s` hit-stun grace). Chests are resolved independently: the same swing also opens every overlapping **unopened** chest (see §F), and an already-opened chest is skipped without consuming the swing. Only while nothing has landed a hit yet this swing does the game then check the map's `secret=true` wall tiles and break at most one overlapping wall (see §2.Z), and if still nothing, a strike overlapping any regular solid `collisionRects` member spawns a **sword-clank spark** at the wall (`ParticleHelper.spawnParticle(engine, GlobalParticles.SPARKS, ...)`, scale `1.2`, hard `maxLifetime` `1.0s` — the same constants `EnemyDamageResolver` uses for enemy hit sparks, see §2.I) so a swing into a wall reads as a "hit" without a breakable-tile side effect. `meleeHasHit` is set the first time anything hits (enemy, chest, wall break, or clank) so the one-shot wall-break/clank effects fire at most once per swing, and `update()` `meleeAttack` runs every frame the swing is active. The current frame's strike rectangle is always exposed via `MeleeAttackSystem.getActiveStrikeBounds()` so the SHIFT+D debug overlay can draw it in red (see §2.D).
5.  **Animation & Visual Feedback:** Trigger the `ATTACKING` animation state while `meleeAttack.isActive()`, taking priority over movement-derived states (idle/run/jump/wall-climb); a distinct attack-pose texture is registered for this state so the strike is visibly obvious on-screen. The `ATTACKING` clip is authored ~**2.5× faster** than the other action clips in `PlayerFactory.attachPlayerAnimations` (`0.04s`/frame vs `0.1s`), so a swing reads snappy; because `meleeCooldown`/`meleeAttack` durations are derived from the animation duration, the faster clip also tightens the strike window and cooldown consistently.
6.  **Facing Flip:** Every frame, the player's `transform.scale.x` is set to `Math.abs(transform.scale.x) * facingDirection`, mirroring the sprite horizontally to match the direction the player last moved/faced (the renderer already scales draw width by `transform.scale.x`, so a negative value flips the sprite for free).

### D. Ammo-Gated Shooting Logic (`PlayerInputSystem` & Spawning)
1.  **Input:** Listen for the Special button (**Y**, keyboard `K` or keyboard `Y`), independent of the melee button.
 2.  **Cooldown & Ammo Check:** Only allow shooting if `shootCooldown.isDone()` **and** `ammo > 0`. If ammo is 0, the request is silently dropped: no bullet is spawned and `shootCooldown` is left untouched (mirroring the cooldown-drop behavior).
 3.  **Entity Creation:** On a successful shot, decrement `ammo` by 1 and instantiate a new projectile entity dynamically with:
    *   `TransformComponent`: Positioned at the player’s center, offset slightly forward based on `facingDirection`.
    *   `MovementComponent`: High horizontal velocity multiplied by `facingDirection` ($X \text{ velocity} \times \text{direction}$), with $0$ vertical velocity.
    *   `TextureComponent`: A small projectile/energy pixel sprite.
    *   `CollisionComponent`: Small bounding box for impact detection.
    *   `BulletComponent`: Set lifetime to roughly 1.5 seconds and `damage = 10` (`BULLET_DAMAGE`).

### E. Pickup Logic (`PickupSystem`)
1.  **Lookup:** Resolve the single player entity once when the system is added to the engine (mirroring `PlayerBulletSystem`'s enemy lookup pattern).
2.  **Overlap Check:** For each pickup entity (`DaggerPickupComponent`, `CoinPickupComponent`, or `PotionPickupComponent`, spawned from `"dagger"`/`"coin"`/`"potion"` object-layer markers or chest drops), check AABB overlap between its `CollisionComponent` bounds and the player's.
 3.  **On Overlap:** For a dagger pickup, increment `player.ammo` by the pickup's `amount`, capped at `maxAmmo` (no overflow past the cap). For a coin pickup, increment `player.coins` by the pickup's `amount` (uncapped, reflected immediately by the HUD's existing coin counter) and spawn a one-shot sparkle burst at the coin's center via `ParticleHelper.spawnParticle(engine, GlobalParticles.SPARKS, ...)` with a hard `1.5s` max lifetime so the sparkle is brief and never lingers. For a potion pickup (see §2.E.1), add `1` to the matching held-potion count, capped at `GameConstants.POTION_CAP` — an over-cap pickup converts to `GameConstants.POTION_OVERFLOW_COINS` coins instead (so a full inventory still rewards the player, without a silent no-op). Either way, remove the pickup entity from the engine.

### E.1. Potion Pickup, Selection, Consumption & Inventory (`PlayerInputSystem`, `BuffSystem`, `InventoryBarStage`)
 1.  **Pickup:** `PotionPickupComponent` carries a `PotionType` (healing/strength/speed/invulnerability); the shared pickup flow of §2.E.3 adds it to the matching count on `PlayerComponent`, capped at `POTION_CAP` (over-cap converts to `POTION_OVERFLOW_COINS` coins). Each potion type has its own pickup sprite (`assets/gfx/old/potion_<type>.png`, exposed via `PotionType.iconPath()`) so the HUD/hotbar icons always match the held item.
 2.  **Selection (cycle):** `PlayerComponent.selectedPotion` names the next potion to drink, defaulting to `HEALING`. The player cycles it with the **Z** key (desktop): `cyclePotion()` advances `selectedPotion` through `PotionType` values (`HEALING → STRENGTH → SPEED → INVULNERABILITY → HEALING`). Cycling is allowed even during hit-stun (but not while dead).
 3.  **Consumption (use, keyboard quick-drink):** Pressing **C** (desktop) attempts to drink: it must not be dead, `potionCooldown` must be `isDone()` (started for `POTION_USE_COOLDOWN = 0.4s` on every successful drink, so chugging is rate-limited), and `consumeSelectedPotion()` must find at least `1` of the selected type (it decrements the count and returns true). **Drinking is allowed during hit-stun** — it's the clutch-heal escape hatch — only death blocks it.
 4.  **Effects:** the shared `com.axehigh.platformer.util.PotionEffects.apply(playerEntity, player, type)` resolves by type — used by both the **C** quick-drink and the inventory hotbar. **Healing:** `health = min(maxHealth, health + HEALING_POTION_HEAL)` (one heart, still capped at max). **Strength:** `buff.startStrength()` for `STRENGTH_BUFF_DURATION = 20s`; while active, `MeleeAttackSystem` doubles `player.swordDamage` on every strike (see §2.C.4), and a "Double strength!!" floating message appears. **Speed:** `buff.startSpeed()` for `SPEED_BUFF_DURATION = 15s`; while active, `BuffSystem` scales `movement.maxSpeedX` by `SPEED_MULTIPLIER = 1.5` each frame (caching the pre-buff base in `speedBaseMaxSpeedX`, re-asserting every frame so a level swap that resets `maxSpeedX` can't silently cancel the buff, and restoring the base when it expires) and sets `player.maxJumps = 3` for triple jump (restored to `2` on expiry); a "Triple jump!!" floating message appears. **Invulnerability:** `buff.startInvulnerability()` for `INVULNERABILITY_DURATION = 10s`; while active, `PlayerDamageResolver` ignores all damage (see §2.J) with no knockback and no `hitInvulnerability`/`hurtTimer`. The HUD shows the selected potion's icon and held count next to the coin counter.
  4a.  **Buff feedback (in-world halo + HUD countdown):** While any Strength/Speed/Invulnerability buff is active, `BuffSystem` attaches a single `LightComponent` to the player entity, drawn by the existing torch-light pass (§2.Y, purely cosmetic additive glow): radius `56`, centered mid-body (`offset.y` = the collision box's vertical center), tinted with the **component-wise average** of the active buffs' `PotionType` colors (alpha 1) so mixed buffs blend smoothly; when no buff is active the halo is removed entirely. Once the soonest-expiring active timer drops under `BUFF_BLINK_THRESHOLD = 3s`, the halo blinks — `baseAlpha` alternates between `0.85` (bright) and `0.15` (dim) on a `BUFF_BLINK_INTERVAL = 0.2s` toggle — and holds steady at `0.85` while more time remains. The top-center HUD mirrors this with a buff countdown row in `HudStage` (below the selected-potion indicator): one potion icon + remaining-seconds label (`ceil`, e.g. `20`) per active buff type, refreshed every frame; an entry is hidden while its buff is inactive, its **icon blinks** (~5Hz) during that buff's own final 3 seconds, and the label counts down normally.
  5.  **Inventory hotbar (`InventoryBarStage`):** A horizontal row of **one slot per `PotionType`** (icon + held count, each slot on a dark panel), drawn at the bottom-center **on top of** the touch controls. It opens via the **I** key or the backpack button in the bottom-right touch-control cluster (the leftmost button of the A/B/Y row, `TouchControlsStage` — on desktop without touch controls the **I** key is the only opener). Opening the bar is a pure HUD toggle: the game **keeps running** while it is open (no `gamePaused`, no engine freeze); **ESC**, the backpack button, or a tap anywhere outside the slots closes it again (the bar sits before the touch controls in the input multiplexer while open, so its slots always win taps that overlap the buttons beneath). Tapping an enabled slot drinks one potion of that type (`consumePotion(type)` → `PotionEffects.apply(...)`, sharing the `potionCooldown` rate-limit with the **C** quick-drink, with a click SFX). A slot is disabled while its count is 0, while the drink cooldown is active, or — for **Healing** — while health is already full; disabled slots are dimmed and ignore taps. The bar stays open after drinking so several potions can be drunk in a row. The player cannot open the bar while dead or while the game-over dialog is up.
 6.  **Persistence:** The four held-potion counts are saved in `SaveData` (`healingPotions`/`strengthPotions`/`speedPotions`/`invulnerabilityPotions`); the stat mapping lives on `SaveData` itself in both directions — `SaveData.of(player)` (called by `LevelExitSystem.buildSaveData(...)` at every exit-gate transition) and `SaveData.applyTo(player)` (called by `GameScreen` when a save is loaded, see §2.M.6).

### F. Chest Open/Disappear Logic (`MeleeAttackSystem` & `ChestSystem`)
1.  **Open Trigger:** When a live melee strike rectangle (i.e. one on a reach-bearing `ATTACKING` frame — see §2.C.4) overlaps an unopened chest (`ChestComponent.opened == false`), mark it `opened = true`, swap its sprite from the atlas `Chest_01_Locked` region to `Chest_01_Unlocked` (`SpriteConstants.CHEST_CLOSED_REGION`/`CHEST_OPEN_REGION`), and `start()` `disappearTimer` (~0.3s). Chests are built entirely from the atlas by `EntityFactory.createChest(...)` at 1:1 region size (128×128 → one map tile), never from a standalone texture or Tiled tile sprite. A chest that's already `opened` has no further reaction to being struck (no repeated drops).
2.  **Loot Pop (`ChestSystem`):** For each opened chest, `update()` `disappearTimer` every frame; once `isDone()` and the chest hasn't popped yet (`!coinsDropped`), loot spawns at the chest's collision center and `coinsDropped = true` is set. The chest **entity itself stays** in the world as the opened container (no further reaction to strikes, no repeated drops). The loot depends on `ChestComponent.potionType`:
    *   **Coin chest** (`potionType == null`, the default): spawns a random number (`MathUtils.random(2, 6)`) of coin pickup entities via `EntityFactory.popCoins`, each given a random initial velocity: `80`-`140` u/s upward and `±40` u/s horizontal. Because these coins carry a `MovementComponent` (and a `PoppedItemComponent` marker), `MovementSystem` picks them up automatically the next frame: gravity arcs them up and back down, AABB collision keeps them from passing through floors/walls, and — since they have `PoppedItemComponent` — their horizontal velocity is zeroed the instant they first touch ground (see §1.E.1), so each coin visibly pops up and scatters outward before coming to rest in place rather than either sitting still or sliding forever.
    *   **Potion chest** (`potionType` set via the `potionType` Tiled object property, e.g. `potionType=healing`): spawns a single popped potion pickup via `EntityFactory.popPotion` at the chest center — the potion launches with a random upward velocity (80–140 u/s) but **no horizontal scatter**, so it pops straight up then falls back down (via `MovementComponent` + `PoppedItemComponent`). Potions are rendered at 37.5% tile scale (75% smaller than the original 50% scale) so they don't dominate the screen. The potion uses the standard `PickupSystem` flow (§2.E.1) — added to the player's held-potion inventory, or converted to coins if at cap. Potion chests use the same `Chest_01_Locked`/`Chest_01_Unlocked` sprites as coin chests (no visual distinction before opening).
3.  **Scope:** This pop-then-fall treatment is shared by chest coin drops (§2.F.2) and enemy death coin drops (§2.G.10); coin/dagger pickups placed directly on the map via object-layer markers are still built with the plain `EntityFactory.createCoinPickup`/`createDaggerPickup` (no `MovementComponent`), so they remain positionally static (coins still spin in place via `AnimationSystem`).

### G. Enemy Patrol Movement Logic (`EnemySystem`)
1.  **Spawn:** Enemies are placed on the map via `"enemy"` object-layer markers, instantiated by `EntityFactory.createEnemy`, which gives them a `TransformComponent`, `MovementComponent`, `CollisionComponent`, and an `EnemyComponent` whose `originX` is set to the spawn X. To desync patrols (enemies otherwise all spawn with identical state on the same frame and move/pause in lockstep), each enemy's initial `direction` is randomized (50/50) and its `speed` is jittered ±15% at spawn, so enemies drift out of phase over time and never re-sync.
2.  **Hit-Stun Pause:** Every frame, `EnemySystem` first `update()`s `enemy.hitStun`; while it's `isActive()`, patrol AI is skipped entirely for that frame so a knockback pop (see §2.I) can play out via `MovementSystem` uninterrupted.
3.  **Velocity Drive:** Otherwise, before `MovementSystem` integrates positions, `EnemySystem` sets `movement.velocity.x = enemy.speed * enemy.direction`.
4.  **Turn-Around Conditions:** `enemy.direction` flips when any of the following is true (checked in this order, first match wins): (a) the enemy is `grounded` and its `velocity.x` was zeroed (meaning `MovementSystem` stopped it against a wall the previous frame — skipped for exactly one frame after a turn pause or a room unfreeze, since that velocity zero comes from the pause/freeze rather than a wall); (b) a **ledge/platform-edge probe** finds no solid ground just past the enemy's leading foot (see "Platform-Edge Detection" below); (c) a **hazard probe** finds a spike/lava `hazardRect` just past its leading foot (see "Hazard Avoidance" below); (d) in `PATROL` mode only, `transform.position.x` reaches `originX ± patrolRange` (skipped entirely in `SIDE_TO_SIDE` mode — see §2.G.11).
5.  **Platform-Edge Detection:** While `grounded`, `EnemySystem` checks a small rectangle positioned just past the enemy's leading foot (in its current travel `direction`) and just below its feet against the same static `collisionRects` set `MovementSystem` uses for wall/floor collision. If nothing overlaps it, there's no platform ahead, so the enemy turns around immediately rather than walking off the edge — this makes it safe to place an enemy on a platform narrower than `patrolRange` without any manual tuning; `patrolRange` still works as an optional secondary cap on top of this (e.g. to keep an enemy patrolling only part of a long platform).
5a. **Hazard Avoidance:** The same `grounded`-gate that drives the ledge probe also drives a second probe checked against the shared `hazardRects` set (the map's spike/lava tiles, the same array `HazardSystem` uses): a rectangle from the enemy's feet up (`40` world units, scaled by `unitScale`) extending just past its leading foot (`16` units ahead). If it overlaps a hazard, the enemy turns around before walking into it. This applies to **every** grounded enemy in **both** modes, so `PATROL` and `SIDE_TO_SIDE` walkers both refuse to cross spike/lava terrain (turn pause included). Flyers are never `grounded`, so this probe never fires for them.
6.  **Physics for free:** Enemies are **not** excluded from `MovementSystem`'s family (only bullets are), so gravity, ground snapping, and AABB wall collision against `collisionRects` apply to them automatically; `EnemySystem` only ever touches horizontal (and, during knockback, vertical) velocity.
7.  **Damage:** Enemies start with `10` hit points (`EnemyComponent.health`) by default, though the exact value varies by tier (`5`/`10`/`15` HP — see "Stat-threshold combat balance tiers" in `resources/docs-ai/enemies.md` §2) and remain damageable via `PlayerBulletSystem` (bullet hits, `10` damage) and `MeleeAttackSystem` (melee strikes, `player.swordDamage` — base `5`, or `8` post-"Sharp Edge", see §2.O), both routed through the shared `EnemyDamageResolver.applyHit(...)` helper (see §2.I).
8.  **Enemy catalog:** This section describes the shared patrol/hit-reaction mechanics; for the concrete enemy type(s) built on top of them (sprite, stats, and guidance for adding more types), see `resources/docs-ai/enemies.md`.
9.  **Death Sequence:** When an enemy's health reaches zero, it enters the `DEATH` state. Its horizontal and vertical velocity are zeroed immediately, it stops patrolling/shooting/contact-damaging the player, and it plays its `DEATH` animation. The entity then **lingers**: the death animation plays out (the `DEATH` clip, tracked by `deathTimer`), and once the timer drops to `EnemyDamageResolver.DEATH_FLASH_DURATION` (`0.8s`) or less remaining, the corpse **blinks** at ~10Hz (the same region-null blink `AnimationSystem` uses for the player's invulnerability) before the entity is removed from the engine by `EnemySystem`. The corpse stays fully inert throughout — no patrol, no contact damage.
10. **Coin Drop on Death:** The coin drop spawns **immediately on the kill** — on the first frame `EnemySystem` observes the death, well before the corpse's linger/blink finishes. One coin per full `5` points of `EnemyComponent.maxHealth` (`floor(maxHealth / 5)`), giving `2` coins for a `10` HP walker/shooter, `1` for the `5` HP flyer, and `3` for the `15` HP knight. Each coin is spawned via the shared `EntityFactory.popCoins(...)` helper — the exact same random-velocity pop (see §2.F.2) used by chests — so killed enemies reward the player with a small, scattershot coin burst the moment the killing blow lands.
11. **AI Modes (`aiMode`):** `EnemyComponent.aiMode` selects the patrol behavior, chosen per-marker via the Tiled `aiMode` property (`"side-to-side"`/`"sidetoside"`, case-insensitive → `SIDE_TO_SIDE`; anything else/absent → `PATROL`). **`PATROL`** is the classic origin-bounded walk of §2.G.4(d) — `patrolRange` from `originX`, plus walls/ledges/hazards. **`SIDE_TO_SIDE`** skips the `originX ± patrolRange` bound entirely: the enemy walks endlessly, turning only on walls, ledges, and hazards — the mode is aimed at ground-walking enemies on wide floors. A `SIDE_TO_SIDE` flyer is unaffected (its grounded-gated probes never fire, so it still turns on the range bound).
12. **Turn Pause:** Every turn-around (wall, ledge, hazard, or `PATROL` range limit) calls `EnemySystem.turnAround(...)`, which flips `direction` **and** starts `enemy.turnPause` for `0.3s` (scaled by `unitScale`). While `turnPause` is active the enemy's `velocity.x` is zeroed and patrol is skipped, so each turnaround visibly stops the enemy before it resumes walking. On the single frame right after the pause expires, the wall/range checks are skipped once so the still-zeroed velocity and still-at-limit position don't spuriously re-trigger a turn.

### I. Enemy Hit Reaction: Stun + Knockback (`EnemyDamageResolver`)
1.  **Shared resolver:** Both `PlayerBulletSystem` (bullet hits) and `MeleeAttackSystem` (melee hits) route enemy damage through a shared `EnemyDamageResolver.applyHit(enemy, movement, damage, knockbackDirection, isFlying)` helper, so both damage sources react identically. `isFlying` is computed at each call site from whether the hit enemy has a `FlyingEnemyComponent`.
2.  **Immunity while stunned:** If `enemy.hitStun.isActive()`, the hit is ignored completely — no damage, no knockback — preventing a single swing/bullet from re-triggering the pop on an enemy still mid-knockback.
3.  **Damage & knockback:** Otherwise, `damage` is subtracted from `enemy.health`. If health reaches 0, the enemy enters the death sequence (see §2.G.9). Otherwise, its `MovementComponent.velocity.x` is set to a knockback pop: `90` u/s horizontally away from the attacker (melee: opposite the player's `facingDirection`; bullet: the bullet's own travel direction, via `knockbackDirection`). Unless the enemy has a `FlyingEnemyComponent` (see §2.K), a `140` u/s upward hop is also applied to `velocity.y`; for a flying enemy this vertical hop is skipped entirely (it has no gravity to pull it back down, so it would otherwise drift upward forever) while the horizontal pop still applies.
4.  **Grace period:** A surviving hit also `start()`s `enemy.hitStun` for at least `0.3` seconds (matching the `HURT` animation duration); while active, `EnemySystem` pauses patrol AI (§2.G.2) so the knockback isn't immediately overwritten, and the enemy can't take further damage until it elapses.
5.  **Hit spark:** Every surviving hit also spawns a one-shot spark burst at the enemy's collision center (`ParticleHelper.spawnParticle(engine, GlobalParticles.SPARKS, ...)`, scale `1.2`, hard `maxLifetime` `1.0s`). The `sparks` effect is continuous, so the hard cap is what stops it from lingering ~4s; the same constants feed the player's sword-clank on solid walls (§2.C.4).
5.  **Post-hit idle:** Once `hitStun` expires, `EnemySystem` automatically `start()`s `enemy.postHitIdle` for `0.5` seconds. During this period, the enemy's velocity is zeroed (stopping the knockback drift) and the AI remains paused. The `AnimationSystem` displays the `IDLE` state while this timer is active. After it elapses, the enemy resumes its normal patrol.

### J. Player Hit Reaction: Hurt, Knockback, and Invulnerability (`EnemyContactSystem`, `PlayerDamageResolver`)
1.  **Shared resolver:** Enemy touch (`EnemyContactSystem`), enemy melee attack (`EnemyAttackSystem`), enemy bullet (`EnemyBulletCollisionSystem`), and static hazards (`HazardSystem`) all route player damage through the shared `PlayerDamageResolver` helper, so every damage source reacts identically — the player-side mirror of `EnemyDamageResolver` (§2.I). Contact and bullet hits use `applyHit(playerEntity, player, movement, knockbackDirection)`, which applies the small knockback pop (§2.J.4); hazards use `applyHitWithoutKnockback(playerEntity, player)` (see §2.X).
2.  **Immunity while invulnerable:** If `player.hitInvulnerability.isActive()`, the hit is ignored completely — no health loss, no knockback, no re-trigger — so a single frame with multiple overlapping enemies (or a touch + bullet in the same window) still costs one life. The **Invulnerability potion** buff adds a second, independent guard: while `BuffComponent.invulnerability` is active, `PlayerDamageResolver` also ignores every hit (any damage source), with no health loss, no knockback, and no `hitInvulnerability`/`hurtTimer` started — see §2.E.1.
3.  **Damage:** Otherwise, `player.health` is decremented by `1` (clamped at `0`, never negative). Reaching `0` triggers game-over handling — see §2.P.
4.  **Knockback pop:** `MovementComponent.velocity.x` is set to a small push (`60` u/s) away from the attacker — opposite the enemy's collision-center X for contact, or in the bullet's travel direction for shots. Horizontal-only, no vertical hop (the player has full gravity and the hit-stun lock is brief).
5.  **Hit-stun lock (`hurtTimer`):** A surviving hit `start()`s `player.hurtTimer` for at least `0.3` seconds (matching the `HURT` animation duration, so the clip visibly plays once). While it's active, `PlayerInputSystem` locks the player's input: horizontal movement is left alone (so the knockback slide plays out instead of being overwritten), and jump/melee/shoot are ignored. `MovementSystem` also suppresses the wall-climb latch during this window, so a knockback push into a wall can't fake a wall-grab.
6.  **Hurt animation window:** `AnimationSystem` resolves the `HURT` state from `hurtTimer` (not `hitInvulnerability`), so the non-looping hurt clip plays exactly once and the pose doesn't stay frozen on the last frame. The timer is ticked exactly **once per frame** in `EnemyContactSystem.update()` (alongside `hitInvulnerability`), before iterating enemies.
7.  **Grace period + blink:** The same hit also `start()`s `hitInvulnerability` for `2.0` seconds. Once `hurtTimer` expires but the grace period is still running, the player's animation returns to normal (run/jump/idle) and the sprite **blinks** at ~10Hz (`AnimationSystem` nulls `TextureComponent.region` on alternating phases; a null region is skipped by `RenderSystem`), so the remaining invulnerability is readable without freezing the player in a pain pose. Damage only resumes once `hitInvulnerability` elapses.
8.  **No-knockback variant (`applyHitWithoutKnockback`):** Static hazard tiles call a variant that applies the identical health/stun/grace bookkeeping but leaves `MovementComponent.velocity` completely untouched — a hazard touch hurts without shoving the player, since a fixed tile has no meaningful "attacker direction" (see §2.X). The shared `hitInvulnerability` grace period means a hazard hit and a nearby enemy/bullet hit still share one combined window.

### K. Flying Enemy Movement (`MovementSystem`, `EnemySystem`, `FlyingEnemyComponent`)
1.  **Gravity Opt-Out:** Every frame, `MovementSystem` checks whether the entity has a `FlyingEnemyComponent`; if so, the gravity/wall-slide velocity-Y update is skipped entirely, so the enemy never falls under gravity on its own.
2.  **Vertical Bob Wave:** Every frame patrol AI isn't paused (i.e. `enemy.hitStun` is not active), `EnemySystem` also accumulates `flying.bobTime += deltaTime` and sets `movement.velocity.y = flying.bobAmplitude * flying.bobFrequency * cos(flying.bobTime * flying.bobFrequency)`. Since gravity never touches `velocity.y` for a flyer, `MovementSystem`'s normal integration turns this into a smooth sine oscillation of height, swinging ±`bobAmplitude` (default `8` units) around the height the enemy was at when patrol last resumed, at `bobFrequency` (default `π` rad/s, ≈ 2 second period) — giving the enemy a visible flap/hover instead of flying in a perfectly flat line.
3.  **Horizontal Patrol Unchanged:** `EnemySystem`'s horizontal patrol logic (§2.G) needs no per-flyer changes: since it's never `grounded`, its wall-block, ledge-probe, and hazard-probe turn-around checks (all gated on `movement.grounded`) simply never fire, so it turns around purely on the `originX ± patrolRange` bounds check — meaning a `SIDE_TO_SIDE` flyer (see §2.G.11) skips even that and flies straight, since `aiMode` is aimed at ground-walking enemies.
4.  **Level-Design Constraint:** A flying enemy has no wall-block fallback, so its `patrolRange` must be placed clear of walls by the level designer (there's no automatic edge/wall/hazard avoidance for flyers, unlike grounded patrol enemies); it should also be placed with enough vertical clearance for the bob wave.
5.  **Knockback & Bob Pause:** See §2.I.5 — a flyer's vertical knockback hop is skipped so it doesn't drift upward forever; since patrol AI (and therefore the bob) is paused for the same `hitStun` duration, `bobTime` simply freezes and resumes smoothly once the stun ends.
6.  **Catalog:** See `resources/docs-ai/enemies.md` for the Flying Enemy's stats (5 HP).

### L. Enemy Shooting & Enemy Bullet Damage (`EnemyShootSystem`, `EnemyBulletCollisionSystem`)
1.  **Firing Cadence:** A shooter enemy (`EnemyShooterComponent`) still patrols exactly like a base enemy (driven by `EnemySystem`, since it matches its family too). Every frame, `EnemyShootSystem` ticks `shooter.shootCooldown`; while `enemy.isDead` (§2.G.9) or `enemy.hitStun.isActive()` (§2.I), firing is skipped entirely, mirroring `EnemySystem`'s own stun-pause. At spawn the cooldown is started at a random offset (uniform over one `shootInterval`), so shooters don't all fire on the same frame the player first enters their room — subsequent shots stay desynced since each restarts its own cooldown independently.
2.  **Same-Room Gating:** Once `shootCooldown.isDone()`, `EnemyShootSystem` additionally checks whether the shooter's `EnemyComponent.roomIndex` is either `-1` or equal to `RoomState.activeRoomIndex` (see §2.N), and only proceeds to fire if so. If the shooter's room isn't the active one, it simply doesn't fire that frame and leaves `shootCooldown` at `isDone()` (never restarted), so it fires immediately once its room becomes active again instead of firing blind into a room the player isn't even in.
3.  **Spawn:** When both the cooldown and the room check pass, a bullet is spawned at the enemy's leading edge, traveling horizontally in `enemy.direction` — there is **no** player-aiming/aggro, the shot always fires in whatever direction the enemy is currently facing/patrolling. The cooldown then restarts via `shootInterval` (`5` seconds by default).
4.  **Enemy Bullet Tagging:** The spawned bullet gets both `BulletComponent` (`damage = 0`, unused for enemy bullets) and `EnemyBulletComponent`, a marker that makes `PlayerBulletSystem` ignore it (excluded from its family) so it's instead processed by `EnemyBulletCollisionSystem`.
5.  **Hit Resolution (`EnemyBulletCollisionSystem`):** Mirrors `PlayerBulletSystem`'s bullet-vs-wall/lifetime handling, but resolves the hit case against the cached player entity instead of an enemy via the shared `PlayerDamageResolver` (§2.J), with the knockback pushed in the bullet's own travel direction. On overlap, the bullet is always removed and the full player hit-reaction (health decrement, hurt window, knockback, invulnerability) applies exactly like being touched by an enemy — sharing the same `hitInvulnerability` grace period (§2.L.6). Bullets already in flight are unaffected by the room check — only new shots are gated.
6.  **Shared Grace Period:** This is the **same** `player.hitInvulnerability` timer `EnemyContactSystem` (§2.J) uses, so a shot landing right after a contact hit (or vice versa) within the same window doesn't stack — a shot costs a life "similar to being hit by an enemy," per design.
7.  **Catalog:** See `resources/docs-ai/enemies.md` for the Shooting Enemy's stats (10 HP, 5s shot interval).

### M. Enemy Melee Attack (`EnemyAttackSystem`, `EnemyAttackComponent`)
1.  **Overview:** Non-shooter enemies (walkers, flyers, knights) can perform a melee attack against the player when within range, resolved by `EnemyAttackSystem`. The attack consists of a wind-up telegraph followed by a strike. Shooter enemies do NOT get melee attacks by default (they already have ranged attacks), though the Tiled `attackType` property can override this.
2.  **Component:** `EnemyAttackComponent` is layered on top of `EnemyComponent` and holds: `attackType` (enum: `MELEE`), `attackInterval` (cooldown between attacks, default `2.0s`), `windUpDuration` (telegraph duration before damage, default `0.4s`), `attackRange` (front strike-commit distance in world units before `unitScale`, default `24`), `detectionHeight` (total height of the centered detection box before `unitScale`, default `20` = 1.25 tiles), `strikeWindow` (live "blade out" damage window, default `0.2s`), `attackDamage` (default `1`), `recoveryDuration` (post-strike wind-down, default `0.5s`), and `recovery` (the wind-down `Timer`). Four `Timer` instances track state: `attackCooldown` (counts down between attacks), `windUp` (counts down during the wind-up phase), `strike` (counts down during the live strike window), and `recovery` (started when a strike resolves; holds the enemy stationary). There is **no awareness latch** — detection is strictly live per frame.
3.  **Detection (live, omni-directional):** Each frame, `EnemyAttackSystem` computes the player/enemy center X/Y from their collision `worldBounds` (matching `EnemyContactSystem`) and checks a box **centered on the enemy's AABB center**: `attackRange × 3 × unitScale` wide per horizontal side and `detectionHeight` (`20` = 1.25 tiles, `±10u` per side) × `unitScale` tall total. The player's *center* inside it counts as detected. Detection alone triggers chase only — a strike still needs the front commit rectangle to overlap (see 5).
4.  **Chase:** While the player is detected, `EnemySystem` stops patrolling and moves the enemy toward the player with normal movement (`velocity.x = speed * direction`, or `0` when a wall/ledge/hazard blocks), **never turning away** — a blocked enemy holds in place, still facing the player. The chase branch runs whenever the player is detected and skips all patrol turn/range logic (`turnAround`, `patrolRange`). Facing re-snaps to the player only while the horizontal center-distance exceeds `1u`, preventing facing jitter.
5.  **Attack trigger (commit):** A strike commits when all three hold at once: `attackCooldown.isDone()`, the player currently detected, **and** the player's `worldBounds` overlapping the **front commit rectangle** adjacent to the enemy's facing edge — `attackRange × unitScale` wide, collision height tall, aligned to `worldBounds` — so the enemy never swings at a player behind it, and while detected-but-out-of-commit-range it chases. On commit the enemy snap-faces the player (`enemy.direction = sign(centerX difference)`), resets the stale `strike` timer, starts `windUp`, sets `isAttacking = true`, and zeroes `velocity.x`. While merely detected/out-of-cooldown it does **not** zero patrol velocity — the enemy keeps chasing. Once `isAttacking` is set: `EnemySystem` fully pauses patrol for the whole attack (velocity `x`—and `y` for flyers—zeroed, facing locked), and `EnemyAttackSystem` keeps zeroing `velocity.x` each frame so the telegraph plays cleanly stationary. Facing is locked for the entire wind-up, so the swing always lands in the direction the enemy committed to.
6.  **Attack sequence:** (a) Wind-up phase: `windUp` counts down while the `ATTACKING` animation plays (see §2.C.5). (b) When `windUp.isDone()` the **strike window** opens for `strikeWindow` (`0.2s` default): a live strike hitbox — *the enemy's own collision width* × height, adjacent to its facing edge, aligned to `worldBounds` — is exposed via `EnemyAttackSystem.getActiveStrikeBounds()` (non-`null` only while live, mirroring the player's blade-out) and checked against the player's `worldBounds` every live frame. (c) On overlap, damage is applied via `PlayerDamageResolver.applyHit(...)` with knockback direction toward the player — the shared `2.0s` invulnerability grace period applies, so repeated overlaps within the same window can't stack damage. (d) When the window ends, the attack ends, `attackCooldown` restarts at `attackInterval`, and `attack.recovery` starts the `recoveryDuration` (`0.5s`) **wind-down**: the enemy stands still, facing locked (patrol fully paused, same as the wind-up), so after a swing — hit or whiff — the enemy keeps facing the direction it attacked. When the recovery ends it resumes **chasing** if the player is still detected, otherwise patrolling **in that same direction**: the frame the recovery ends skips only the wall-block turn check (`resumedFromAttack = wasRecovering`), because the recovery-zeroed velocity would otherwise be misread as a wall collision and flip the enemy right after it swung; ledge/hazard/patrol-range turn logic applies normally from that frame on, so the enemy still never walks off a ledge.
7.  **Telegraph Window:** The wind-up provides a visible telegraph before damage — the enemy plays its `ATTACKING` animation during this phase, giving the player time to dodge. The wind-up does NOT deal damage; only the strike at the end does. The enemy is stationary and facing-locked for the whole telegraph, and the strike direction is locked with it.
8.  **Same-Room Gating:** Like `EnemySystem`/`EnemyShootSystem`, a melee attacker whose `roomIndex` isn't the currently active room (see §2.N) never attacks — its room is frozen, so it can't lunge while the player is building rooms away. `attackCooldown` keeps ticking regardless, so the enemy is armed for an instant lunge the moment its room becomes active.
9.  **Cooldown Stagger:** At spawn, `EnemyFactory` starts the `attackCooldown` at a random offset (`MathUtils.random(0, attackInterval)`) so multiple enemies don't all attack on the same frame — identical to the shooter's cooldown stagger pattern.
10. **Tiled Configuration:** Attack parameters are configurable from Tiled marker properties: `attackType` (string: `"melee"` or absent), `attackInterval` (float, seconds), `attackRange` (float, world units; legacy alias `meleeRange` still honored), `windUpDuration` (float, seconds). Non-shooter enemies default to `attackType = "melee"` when the property is absent; shooter enemies default to no melee attack.
11. **Stun/Recovery Immunity:** If `enemy.hitStun.isActive()`, `enemy.postHitIdle.isActive()`, or the post-strike `recovery` stand is active (the enemy was recently damaged or is still winding down from its last swing), the attack system skips the trigger entirely — the enemy can't attack while stunned, recovering, or mid-wind-down, mirroring `EnemySystem`. An attack in progress is NOT cancelled; it simply doesn't process until the stun ends, so the wind-up timer effectively pauses.
12. **Shared Grace Period:** The damage goes through `PlayerDamageResolver.applyHit(...)`, which checks `player.hitInvulnerability` — the same grace period shared by contact damage (§2.J), enemy bullets (§2.L.6), and hazards (§2.X). So an enemy melee hit and any other damage source within the same `2.0s` window still only costs one life.

## 3. Collision & Cleanup Systems

### A. Projectile Collision Handling
Create or expand a `PlayerBulletSystem` to handle bullet interactions:
*   **Wall Impact:** If a bullet entity's bounding box intersects a solid Tiled layer cell, immediately remove the bullet entity from the engine. Exception: a freshly-spawned bullet is exempt from wall culling while `BulletComponent.elapsed < SPAWN_GRACE` (a short grace window), so a bullet that spawns overlapping a wall tile (e.g. firing directly against a wall) gets a frame or two to move clear instead of being removed on its very first frame.
*   **Enemy Impact:** If a bullet intersects an enemy entity, apply damage to the enemy's health component and destroy the bullet.

### B. Memory Optimization
*   **Bullet Pooling:** Because projectiles are frequently created and destroyed, utilize libGDX’s `Pool` or Ashley's component pooling interfaces to avoid garbage collection stuttering during heavy combat sequences.

### C. Room-to-Room Passages (`MapLoader`)
A multi-room `.tmx` map (see the Room-Based Camera design, §2.N) lays adjacent rooms out as room-sized (or larger/smaller) blocks separated by ordinary wall tiles. Rooms are **never** connected via door objects/interactions; instead, a natural passageway is carved directly into the collision tile layer:
*   **Solid tile property:** Every tile in the collision layer's tilesets declares a boolean `solid` property (`true` for the regular wall tile, `false` for the dedicated `passage_tile`). `MapLoader.buildCollisionRects()` only emits a boundary `Rectangle` for cells whose tile is `solid` (defaulting to `true` if the property is absent), so `passage_tile` cells render as part of the wall/corridor art but never block movement.
*   **Authoring an opening:** To connect two adjacent rooms, replace the wall tiles on **both** sides of the shared border (each room contributes its own 1-tile-thick border) with `passage_tile` cells, spanning enough width/height for the player to walk through comfortably (e.g. 3-4 tiles).
*   **No new components/systems required:** Since passability is derived purely from the tile's `solid` property, traversal, `MovementSystem`'s AABB collision, and `PlayerBulletSystem`'s bullet-vs-wall checks all treat a passage exactly like open floor — no special-casing needed outside `MapLoader`.

### D. Debug Collision Overlay (`DebugRenderSystem`)
A dedicated `DebugRenderSystem` (see `resources/docs-ai/ashley-ecs.md`) draws every live `CollisionComponent` AABB (lime), the static map `collisionRects` (yellow), the static one-way-platform `oneWayRects` (cyan) and hazard `hazardRects` (red, see §2.W/§2.X), every `RoomState.rooms` rectangle (cyan, with whichever one is currently active in orange — see §2.N), and the player's current melee strike hitbox (red, from `MeleeAttackSystem.getActiveStrikeBounds()`, visible only while a swing is on a reach-bearing frame — see §2.C.4) via a `ShapeRenderer`, toggled on/off with **SHIFT+D** or the pause menu's **"Collision Debug"** button (see `AGENTS.md` "Debugging"). It is a pure visualization aid — disabled by default, no gameplay effect, and skips all drawing while off.

### M. Multi-Level Progression & Exit Gates (`LevelExitSystem`, `LevelManager`, `PlayerInputSystem`)
1.  **Level chain:** The game ships 10 levels in a strict, hardcoded-by-content (not hardcoded-in-code) loop: `maps/world1/level_01.tmx` (level 1, where `GameScreen` boots into `LevelCatalog.levels().first()`) → `level_02` → `level_03` → `level_04` → `level_05` → `level_06` → `level_07` → `level_08` → `level_09` → `level_10`, whose exit gate loops back to `level_01`. Each map's exit gate points at the next one via its own `nextLevel` Tiled property (§1.E.2) rather than any level-order list, so the chain is purely data-driven and could become non-linear later without code changes. The **final level of a world** (e.g. `level_10`, which would otherwise loop) can be marked with `isFinal=true` on its exit-gate object; interacting with it triggers the **victory flow** (`VictoryScreen`, "WORLD N COMPLETE!") instead of looping — see §2.M.10.
2.  **Proximity sensor, not walk-through:** Unlike coin/dagger pickups, an exit gate never auto-triggers on overlap. The gate entity is **logic-only** — `EntityFactory.createExitGate(...)` draws no sprite, so the door's art/decoration is painted by the level designer in the map layers — and sizes its `CollisionComponent.bounds` from the Tiled object rectangle. `LevelExitSystem` builds a sensor `Rectangle` from that bounds inflated by `SENSOR_PADDING = 6` world units on every side (so it feels like walking up to a door, not requiring pixel-perfect contact) and checks it against the player's AABB every frame.
3.  **Interact input:** Pressing **E** (keyboard) or the new contextual up-arrow touch button sets `player.interactPressed` for exactly one frame (`PlayerInputSystem`, mirroring the existing `requestTouchJump`/`touchJumpRequested` one-shot pattern via `requestTouchInteract()`/`touchInteractRequested`). A level transition only fires when the player is inside a gate's sensor **and** `interactPressed` is `true` that same frame; being near the gate alone only sets `player.nearExit = true` (driving the UI prompt) without firing anything.
4.  **Contextual UI prompt & door glow:** `TouchControlsStage` exposes `setInteractVisible(boolean)`, called every frame from `GameScreen.render()` with `playerComponent.nearExit`, showing/hiding a small up-arrow touch button (per the "Contextual Action Button" UI guideline) only while the player is near a gate. In addition, while inside the proximity sensor, `LevelExitSystem` smoothly fades in an amber `LightComponent` (scaling opacity and radius over 0.3s) centered on the exit door, rendering an additive flickering glow halo via `LightRenderSystem` to highlight the interactable door; moving away smoothly fades the glow out and detaches the component once zero is reached.
5.  **In-place level swap (`LevelManager`, with screen-layer fade):** Firing a **non-final** gate no longer calls `LevelManager.loadLevel(...)` directly from `LevelExitSystem`. Instead the system invokes an injected `LevelExitSystem.LevelTransition` callback (`setOnTransition(...)`), which `GameScreen` wires to a **level-transition fade**: the shared screen `fadeOverlay` (from `BaseScreen`) fades out to black (`Actions.fadeIn(LEVEL_FADE_TIMER)`), then calls `LevelManager.loadLevel(nextLevelPath, playerEntity)`, then fades back in (`Actions.fadeOut(LEVEL_FADE_TIMER)`), with input blocked (`Touchable.enabled`, then `disabled`) for the whole 2×`LEVEL_FADE_TIMER` chain. `LEVEL_FADE_TIMER = 1.0s` (a `GameConstants` constant, independent of the 0.5s `SCREEN_FADE_TIMER` used by screen-level swaps) so the level-exit fade reads as a clear, deliberate "fade to black → swap → fade in from black". For this overlay to actually be visible over the gameplay world, `GameScreen` sets `BaseScreen.renderTransitionInBase = false` (so `super.render(...)` skips it) and calls `renderTransition(delta)` as the **last** draw of its own `render()` — after the world/HUD/inventory stages render — keeping the black overlay topmost during every fade. This gives walking through an exit gate the same entry fade-in / exit fade-out used by screen-level swaps. `loadLevel` itself loads the new `.tmx`, swaps `TiledMapRenderSystem`'s wrapped map, clears+refills the shared `collisionRects` array **and** the shared `RoomState.rooms` array in place (every map-dependent system already holds one of those same references, so no re-wiring is needed), removes every engine entity **except** the player, disposes the old map, respawns the new level's objects (`EntityFactory.spawnObjects`, which also assigns each spawned enemy's `roomIndex` — see §2.N), repositions the player at the new map's `playerStart`, and calls `CameraSystem.snapToRoom(..., bandZoom)` to place the camera in the new starting room (the `bandZoom` flag is forwarded from `GameScreen.applyLayoutMode()` via `LevelManager.setBandZoom(...)`). The `PooledEngine` and the player `Entity` are never destroyed — it's the exact same `PlayerComponent` instance before and after the swap. Separately, entering any level (including the initial `GameScreen.show()` and after a gate swap) fades **in** from black via `BaseScreen.show()`'s existing fade-in.
6.  **Stat persistence guarantee:** Because the player entity survives the swap, `health`, `maxHealth`, `coins`, `items`, `maxAmmo`, and every active cooldown `Timer` (shoot/melee/hit-invulnerability) carry over into the new level completely untouched — there is nothing to serialize or restore. Only *transient* state is explicitly reset by `LevelManager`: `MovementComponent.velocity`/`grounded`, and `PlayerComponent.jumpCount`/`isWallClimbing`/`interactPressed`/`nearExit`/`dropRequested`/`onDropTile`/`dropWindow`, so the player doesn't, say, arrive already mid-jump, wall-climbing, or mid-drop-through in the new room.
7.  **Fresh object population:** Every non-player entity from the old level (enemies, pickups, chests, the old exit gate, etc.) is gone after a transition; the new level's enemies/pickups/gate are spawned fresh from its own object layer, exactly as if the level had just been loaded from scratch.
8.  **Cross-session persistence:** Passing through any exit gate autosaves a `SaveData` snapshot (level path, core stats, `completedLevelIds`, `completedWorldIds`, `triesRemaining`) via `SaveManager`/libGDX `Preferences`, so `MainMenuScreen`'s Continue button can resume the run across app restarts — see `resources/docs-ai/main-menu-screens.md`-equivalent plan notes and §2.P for the tries counter specifically.
9.  **Debug overlay survives transitions:** `DebugRenderSystem`'s SHIFT+D toggle state is untouched by a level swap, since the system itself is never removed/recreated — only its `collisionRects`/`RoomState.rooms` references are refilled in place by `LevelManager`.
10. **World-completion / Victory flow (`LevelExitComponent.isFinalLevel`, `VictoryScreen`):** An exit-gate object may carry an `isFinal=true` custom property. `EntityFactory.createExitGate(...)` reads it (via `TileProps.getProperty` + parsing the "true"/"false" string) and stamps it onto the gate's `LevelExitComponent.isFinalLevel`. `LevelExitSystem` branches on that flag at interact time: a **final** gate persists the save (including the just-completed world's id appended to `SaveData.completedWorldIds`) and invokes the injected `onVictory` callback — wired by `GameScreen.show()` through `GameSystems` — which transitions to `VictoryScreen`. `LevelCatalog.worldIdForPath()` maps the current `LevelManager.getCurrentLevelPath()` back to its world id for the screen title. The screen's "Select Level" button always returns to `LevelSelectScreen` (never the main menu). When the beaten world is the catalog's last **real** (non-demo) world — `LevelCatalog.isLastWorld`, `VictoryScreen` instead shows a "YOU WON THE GAME" title over the `splash/win-game.screen.jpeg` backdrop (used **only** then) with a developer-text placeholder ("You have defeated all the monsters, returned to the surface. What will be your next adventure.") — the definitive end-of-game state; any other completed world shows "WORLD N COMPLETE!" over `splash/victory-screen.jpg`. A **non-final** gate behaves via the fade-wrapped level swap described in §2.M.5 (the system's default callback still calls `loadLevel` directly, and the screen-layer callback wraps it in the fade chain).

### MA. Spawn Safety (`SpawnSafety`)
When a level starts (or a mid-game level swap occurs), the engine validates the player's spawn position against the map's solid collision geometry before the player entity is created or repositioned. This prevents the player from spawning inside walls or below floors.

**How it works:**
1. The raw spawn position is read from the Tiled map's `playerStart` object.
2. `SpawnSafety.findSafeSpawn()` checks the position against all solid collision rects:
   - If the player's collision AABB overlaps a solid rect, the player is pushed outward (upward preferred) with a 1-pixel epsilon buffer.
   - If no overlap exists, a vertical probe scans downward to find the nearest floor; the player's feet are snapped to that floor's top surface.
   - If no floor is found below, the position is left as-is (mid-air spawns are intentional).
3. The adjusted position is used as the player's transform position.

**Where it's enforced:**
- Engine runtime: `SpawnSafety` utility called from `GameScreen.show()` and `LevelManager.loadLevel()`.
- Map generator: auto-nudges unsafe spawns upward at generation time with a warning.
- Map validator: rejects maps with spawn positions inside solid tiles.

**Callsites:** `GameScreen.java`, `LevelManager.java`, `SpawnSafety.java`

### N. Room-Based Camera & Entity Management (`CameraSystem`, `RoomState`, `EnemySystem`, `EnemyShootSystem`)
1.  **"Rooms" object layer:** Any map may define an object layer literally named `Rooms`, containing one or more rectangle objects (no `type`/properties needed) — each one is a distinct room zone of whatever size the level designer wants (does not have to match the fixed `VIRTUAL_WIDTH`/`VIRTUAL_HEIGHT` viewport). `MapLoader.getRooms()` parses these into an `Array<Room>` — each a `Rectangle` plus a `Room.Mode` camera-mode override. An optional per-room `camera` custom property (`"flip"` or `"scroll"`) forces that room's camera mode; absent, the mode is **inferred from size** (§2.N.3). A map with **no** "Rooms" layer at all, or with an empty "Rooms" layer (layer present but no rectangle objects), is treated as a **single room covering the whole map** (`MapLoader` synthesizes it from the map's width/height × tile size), so room-less maps still get camera framing and enemy activation across their entire area.
2.  **`RoomState` (shared, live state):** A single `RoomState` instance (created once in `GameScreen.show()`, same sharing pattern as `collisionRects`) holds `rooms` (the current level's parsed `Array<Room>`) and `activeRoomIndex` (which one currently contains the player, `-1` if none). It's passed to `CameraSystem`, `EnemySystem`, `EnemyShootSystem`, `DebugRenderSystem`, `EntityFactory.spawnObjects(...)`, and `LevelManager`, which refills `rooms` in place on every level transition (§2.M.5) — no system ever needs re-wiring across a level swap.
3.  **Hybrid flip-screen / dead-zone scroll camera (`CameraSystem`):** Every frame, `CameraSystem` finds which room rectangle contains the player's position (updating `RoomState.activeRoomIndex`), then positions the camera **per axis** according to that room's resolved mode. "Viewport size" below always means the **effective** size — `camera.viewportWidth/Height × camera.zoom` — so the default `BAND_ZOOM` layout (`com.axehigh.platformer.ui.LayoutMode`, shipped on every platform) zooms the camera in and screen-sized rooms behave like any bigger-than-frame room (dead-zone scroll):
    *   **Flip axis** (room no bigger than the viewport on that axis, or mode `FLIP`): the camera locks to the room's center and stays perfectly static on that axis (the viewport is allowed to show a sliver beyond the room's edges rather than trying to clamp into an impossible range). Entering such a room snaps the camera instantly to its center.
    *   **Scroll axis** (room bigger than the viewport on that axis, or mode `SCROLL`): **dead-zone scroll** — the camera holds its current position while the player roams anywhere more than a screen-edge margin from the edge, and only scrolls once the player crosses that margin (keeping the player at the margin line), clamped so the viewport never shows anything past the room's own edges. The margin is `GameConstants.CAMERA_SCROLL_MARGIN` (`320` px) at zoom 1, but becomes `MOBILE_SCROLL_MARGIN_FRACTION` (30%) of the *effective* (zoomed) view per axis under `BAND_ZOOM` so the zoomed frame starts tracking the player well clear of the screen edges.
    *   A room smaller than the viewport can never scroll, even if forced: `SCROLL` mode on such a room falls back to centering.
    *   There is no smooth lerp/easing on any room-to-room transition — the framing changes instantly the moment the player's active room changes, exactly like the previous flip-screen camera's snap behavior. `CameraSystem.snapToRoom(..., bandZoom)` frames the starting room at level start/swap (§2.M.5): flip rooms center, scroll rooms clamp the player-start into view. When `bandZoom = true` (BAND_ZOOM layout), all rooms use **bottom-left framing** on entry — the camera positions at `roomMin + viewportSize / 2` so the viewport's bottom-left aligns with the room's; small rooms stay fixed there, large rooms scroll to follow the player once they reach the viewport edge. This **replaces** the old fixed-grid flip-screen `CameraSystem` entirely.
4.  **Enemy Room activation (`EnemySystem`/`EnemyShootSystem`):** Each enemy is assigned a `roomIndex` at spawn time (`EnemyComponent.roomIndex`, §1.F) by testing its spawn point against `RoomState.rooms` — no extra Tiled authoring needed. Every frame, both `EnemySystem` and `EnemyShootSystem` check whether that enemy's room is the currently active one (`roomIndex == RoomState.activeRoomIndex`, or always-active if `roomIndex == -1`, e.g. an enemy spawned outside every room rectangle). Because a map with no "Rooms" layer now yields one whole-map room, its enemies get `roomIndex` `0` and are always active — behaviorally identical to the old `-1` fallback. An enemy in an inactive room is **frozen, not despawned**: its horizontal velocity (and, for a `FlyingEnemyComponent`, its bob-driven vertical velocity) is zeroed and all patrol/bob/firing logic is skipped, but the entity itself, its `health`, and its `hitStun` state remain exactly as they were — so leaving mid-fight and coming back later resumes from where you left it, rather than resetting or despawning the enemy. Because the freeze zeroes `velocity.x`, `EnemySystem` sets `EnemyComponent.wasFrozen` while frozen and skips the wall-block turn check for exactly one frame on reactivation — otherwise every grounded enemy in the room would misread that zero as a wall block and flip direction + start its turn pause in unison on re-entry.
5.  **Current level examples:** `level_01.tmx` (1 room `2048x1539`, smaller than the viewport on both axes → static flip framing, whole room always on screen); `level_03.tmx` (2 side-by-side rooms each `2048x2176` → flip each, camera snaps instantly at the `x=2048` boundary; each room is narrower than the viewport, so a sliver of the neighboring room stays visible, which is expected); `level_04.tmx` (no "Rooms" layer → one whole-map room `4096x2176`, only `256` px wider than the viewport → dead-zone scroll; the camera sits pinned for almost the entire map, so the whole level effectively stays on screen while the player roams).
6.  **No effect on collision/movement:** Room rectangles are purely a camera/entity-activation concern; they never participate in AABB collision (that's still `collisionRects`, §3.C) and a room boundary is not itself a wall — the player can walk freely between overlapping/adjacent rooms exactly as the tile geometry allows.

### O. Shop/Upgrade Mechanic (`shop.ShopManager`, `shop.ShopItem`)
1.  **Scope today:** Only the data model and transaction logic exist so far — a standalone, non-ECS `ShopManager`/`ShopItem` pair under `core/.../shop/`. There is no vendor NPC entity, shop map, or interaction UI yet; a future vendor entity/interact prompt is expected to call `ShopManager.purchase(playerComponent, item)` directly, the same way `LevelExitSystem`'s interact prompt already drives a state transition today (§2.M).
2.  **Catalog:** `ShopManager` exposes a fixed 3-item catalog via `getCatalog()`:
    *   **"Sharp Edge"** (`100` gold, one-time): sets `player.swordDamage = 8` and `player.sharpEdgePurchased = true`.
    *   **"Dagger Bandolier"** (`75` gold, one-time): sets `player.maxItems = 60` (doubling the `30` base) and `player.daggerBandolierPurchased = true`.
    *   **"Iron Heart"** (`150` gold, repeatable): increments both `player.maxHealth` and `player.health` by `1`, and increments `player.ironHeartCount`.
3.  **Transaction (`purchase(PlayerComponent, ShopItem)`):** Rejects the purchase with no state change if `player.coins < item.cost`, or if a one-time item (`Sharp Edge`/`Dagger Bandolier`) has already been purchased. Otherwise, deducts `item.cost` from `player.coins`, applies the item's effect, marks the purchased flag (or increments `ironHeartCount` for the repeatable Iron Heart), and returns `true`.
4.  **Combat balance tie-in:** `swordDamage` (base `5`, `8` post-"Sharp Edge") is the same dynamic stat `MeleeAttackSystem` reads on every strike (§2.C.4, §2.G.7); combined with the enemy stat-threshold tiers in `resources/docs-ai/enemies.md` §2 (Grunt `5` HP / Elite `10` HP / Knight `15` HP), a Knight drops from `3` melee hits to `2` once "Sharp Edge" is purchased, while Grunt/Elite hit counts are unchanged by the upgrade.
5.  **Persistence:** In-memory only, matching every other `PlayerComponent` field — upgrades survive level transitions (§2.M.6) for the current play session, but there is no save/load across app restarts.

### P. Player Death, Tries, and Game Over (`PlayerDeathSystem`, `GameScreen`, `SaveData`)
1.  **Detection:** `PlayerDeathSystem` checks `player.health <= 0` every frame. On the very first such frame it sets `player.isDead = true`, zeroes the player's `MovementComponent.velocity` (full freeze — even the lethal knockback doesn't slide the corpse), and starts a death-wait countdown of `max(DEATH animation duration, 0.8s) + 0.5s`. An internal `triggered` guard flips only once, so subsequent frames at `0` health do nothing further. If the player is revived (health restored, e.g. via Continue), the guard re-arms and `isDead` clears, so a later death runs the sequence again.
2.  **Death animation + beat:** While `player.isDead`, the player is fully locked: `PlayerInputSystem` ignores all movement/jump/melee/shoot input and `MovementSystem` suppresses the wall-climb latch, so the frozen body plays its one-shot `DEATH` clip (≈ `1.0s`). The engine keeps updating during this window — `render()` only freezes once the callback fires — so the animation actually renders before anything else happens.
3.  **Kill-plane (out-of-bounds fall):** `PlayerDeathSystem` also watches the player's `TransformComponent`. If the player ever falls below the level's bottom edge (`transform.position.y < -mapWorldHeight`), it forcefully sets `health = 0` so the standard death/Game Over flow fires. This is a safety net for rare cases where a huge frame hitch or an unhandled corner case lets the player slip past the floor; Continue reloads the level and respawns the player safely.
3.  **Delayed Game Over dialog:** Only after the death-wait elapses does the one-time `Runnable` callback fire into `GameScreen`: it sets `gameOverActive = true` and shows the Scene2D `Dialog` (titled "Game Over") on the `hudStage`. While `gameOverActive` is `true`, `render()` skips `engine.update(...)` entirely — no movement, AI, physics, or damage resolves — but `hudStage`'s own `act()`/`draw()` (and therefore the dialog's buttons) keep running. Pause (`togglePause`) is also blocked while `player.isDead`, so ESC/`||` can't interrupt the death animation.
4.  **Tries system:** `SaveData` carries `triesRemaining` (default `3`). A brand-new run (`MainMenuScreen`'s New Game → Story Intro) always clears the persisted save and seeds a fresh `SaveData` with `triesRemaining = 3`; Continue-from-menu resumes whatever value was last persisted. Tries are **not** refilled by level-exit checkpoints — they only ever go down within a run, until New Game restarts the counter.
5.  **Continue (uses 1 try):** Shown only while the loaded/in-memory `SaveData.triesRemaining > 0`. Clicking it decrements `triesRemaining`, persists it immediately via `SaveManager.save(...)`, reloads the **current** level from scratch via `LevelManager.loadLevel(currentLevelPath, playerEntity)` (coins/items/upgrades untouched, since the player entity itself is never destroyed — same guarantee as §2.M.6), resets `player.health = player.maxHealth` and `player.isDead = false`, hides the dialog, and clears `gameOverActive` so the engine resumes updating next frame. This does **not** roll back to the last exit-gate autosave — it restarts the level currently in progress.
6.  **Tries exhausted:** Once `triesRemaining == 0` at the moment of death, the dialog is built with **no** Continue option at all (not merely disabled) — only "Exit to Main Menu" is shown.
7.  **Exit to Main Menu:** Always available regardless of tries remaining; calls `game.setScreen(new MainMenuScreen(game))`, abandoning the current in-progress level (any stats from the last exit-gate autosave remain on disk, untouched).

### R. Pause Menu (`GameScreen`)
1. **Trigger:** The pause menu is triggered by pressing **ESCAPE** or clicking the pause button (`||`) in the HUD.
2. **State:** Setting `gamePaused = true` freezes the Ashley engine update (`engine.update(...)`) in `GameScreen.render()`, effectively pausing all physics, AI, and animations.
3. **Dialog:** A Scene2D `Dialog` (titled "Paused") is shown on the `hudStage`. Its options are split across two tabs selected by a header row of buttons (active tab highlighted in gold; the dialog always opens on Gameplay): **Gameplay** holds Music, Sound Effects, and Wall Climb; **Debug** holds Collision Debug, Touch Debug, Device, and Mobile Layout. Resume and Exit stay outside the tabs so they're reachable from either.
4. **Options:**
    *   **Resume:** Closes the dialog and sets `gamePaused = false`.
    *   *Gameplay tab —* **Music (ON/OFF):** Toggles background music on/off via `AudioManager.setMusicEnabled(...)` (persisted in `GamePreferences`). While paused, the music keeps playing — the toggle is what mutes it.
    *   *Gameplay tab —* **Sound Effects (ON/OFF):** Toggles one-shot SFX on/off via `AudioManager.setSfxEnabled(...)` (persisted in `GamePreferences`).
    *   *Gameplay tab —* **Wall Climb (ON/OFF):** Toggles the wall-climb feature flag live (`FeatureFlags.setWallClimbingEnabled(...)`, persisted).
    *   *Debug tab —* **Collision Debug (ON/OFF) / Touch Debug (ON/OFF):** Toggle the debug overlays (see AGENTS.md "Debugging"); Collision Debug persists per-session, Touch Debug is per-screen.
    *   *Debug tab —* **Device (`AUTO` / `DESKTOP` / `PHONE` / `TABLET`):** Forces a device class for previewing layouts on desktop without a device (see `com.axehigh.platformer.ui.DeviceClass`). Cycling sets a session-wide simulation override, resets the layout to that class's shipped default (all classes default to `BAND_ZOOM`), and on desktop resizes the OS window to a representative shape (phone 2400×1080, tablet 1600×1200) so the band height and letterboxing match the real device. Selecting `AUTO` (wraps in after `TABLET`) clears the override and restores real platform detection. The chosen device — or `AUTO` — and layout persist across app restarts via `com.axehigh.platformer.ui.LayoutPrefs`/`GamePreferences`; a restored device re-applies its window shape on desktop. No-op resize on real mobile backends.
    *   *Debug tab —* **Mobile Layout (`CORNER OVERLAY` / `BAND` / `BAND_ZOOM`):** Cycles the touch-control layout live (see `com.axehigh.platformer.ui.LayoutMode`) so layouts can be A/B-tested without rebuilding; the game viewport band and camera zoom re-apply the same frame. On desktop it auto-switches the device override to `PHONE` first so the overlay is visible for previewing. Shipped default is `BAND_ZOOM` for every view — desktop, mobile, and tablet (world renders above a reserved control strip with the camera zoomed in so tiles stay big, and screen-sized rooms then dead-zone scroll); on non-touch devices the reserved band is skipped and only the camera zoom applies. The choice persists across restarts. The reserved band is capped at a quarter of the screen height (`UI_BAND_SCREEN_FRACTION`) and the touch cluster (D-pad, A/B/Y, contextual buttons) is sized to fit inside it, so the world always keeps at least 75% of the screen; each button's touch target is slightly larger than its visible size (`UI_TOUCH_HIT_PAD`) so taps just outside the drawn button still register.
    *   **Expand-width game viewport (`OffsetFitViewport`):** The game world keeps its fixed height (`VIRTUAL_HEIGHT` × tile scale) but its **width expands with the screen's aspect ratio**, eliminating the left/right black bars (pillarboxing) that plain fit-style viewports show on phones and wide desktops — e.g. a 19.5:9 phone with the control band now fills its whole play region instead of ~20% side bars. Bounds: floored at the classic `VIRTUAL_WIDTH/VIRTUAL_HEIGHT` ratio (narrow/portrait screens keep top/bottom bars as before) and capped at `GameConstants.MAX_WORLD_ASPECT` (~21:9) only for screens that are *physically* ultra-wide, so such monitors never reveal more world than narrower devices; the touch band is deliberately ignored for the cap decision since it would otherwise cost tall phones extra side bars. Pixels stay square at any camera zoom (zoom cancels out of the aspect ratio). `CameraSystem`, `ParallaxBackgroundSystem`, and room flip/scroll inference already read the live `camera.viewportWidth`, so they adapt automatically: wider views turn more rooms into fully-visible flip rooms and widen scroll rooms' dead zones proportionally.
    *   **Exit to Main Menu:** Returns the player to the `MainMenuScreen`.
5. **Interaction:** The pause menu is disabled while the Game Over dialog is active.

### S. Player Scaling (EntityFactory)
1. Scaling Strategy: Automatic. Player scale is derived from tile size to maintain relative size.
2. Atlas Usage: Uses `knight2.atlas` instead of `gfx/player.png`.
3. Implementation: Player `TransformComponent.scale` is set to `unitScale * SpriteCollision.PlayerScale`. `CollisionComponent.bounds` is set to a tighter 40x80 pixel box (scaled by `finalScale`) for more responsive collision handling.

### T. Dynamic Collision Offset & Sprite Alignment (`MovementSystem`, `RenderSystem`)
1. **Alignment & Reach:** The player's collision box can be offset from its visual center using `PlayerOffsetRight`, `PlayerOffsetLeft`, and `PlayerOffsetY` in `SpriteConstants`. These are used to correct sprite misalignment in the atlas or to provide directional reach.
2. **Locked Movement:** The collision box target offset is chosen based on `facingDirection` (`PlayerOffsetRight` when facing right, `PlayerOffsetLeft` when facing left). Vertical offset `PlayerOffsetY` is applied constantly.
3. **Smoothing:** `MovementSystem` smoothly interpolates `CollisionComponent.currentOffsetX` towards the target offset using a lerp, preventing position snaps when turning against walls.
4. **Visual Anchoring:** `RenderSystem` anchors the sprite such that the character's center remains locked to the collision box center (compensated for offsets). To prevent the character from "jumping" in world space when flipping off-center frames, the system dynamically compensates by flipping the sign of the directional offsets (`currentOffsetX/Y`) when calculating the sprite's `frameCenterX/Y`. This ensures that both the character and its collision box remain stable and aligned during turns, even if the character is not centered in the sprite frame.

### V. Moving Platforms (`EntityFactory`, `MovingPlatformComponent`, `MovingPlatformSystem`)
1. **Map authoring:** A moving platform is a rectangle (or tile) in the **"objects"** object layer with `type="platform"`. The object rectangle defines both the sprite footprint and the collision box; a plain rectangle without a tile falls back to the atlas `Chest_01_Unlocked` region (`SpriteConstants.CHEST_OPEN_REGION`, same origin-game.atlas art as the chest's open state), stretched to the rectangle's size. Custom properties:
    *   `amplitudeX` / `amplitudeY` — travel distance in world units per axis around the object's spawn rectangle (default `0`, i.e. a static platform).
    *   `axis` — convenience: `"x"` (amplitudeY forced 0), `"y"` (amplitudeX forced 0), `"both"`/absent (use the amplitude properties as given).
    *   `speed` — oscillation angular frequency in **radians per second** (default `1`; ≈ full back-and-forth cycle every 6.3s at amplitude 1).
    *   `phase` — phase offset in radians (default `0`), for desyncing several platforms.
2. **Motion:** The platform oscillates as `position = base + amplitude * sin(angle + phase)` per axis, where `angle` accumulates at `speed` rad/s. It has **no** `MovementComponent`, so gravity never applies and the motion is purely scripted by `MovingPlatformSystem` (which runs after `MovementSystem` and after `CollisionBoundsSystem`, before the camera/animation/rendering).
3. **One-way top solidity:** Only the platform's **top** surface is solid. A player falling onto it lands (feet snap onto the top surface, `grounded = true`, `jumpCount` reset) and is **carried** along with the platform's motion; jumping up through a platform from below works untouched, and a platform never pushes a player sideways out of its path.
4. **Carrying:** While standing on a moving platform the player is moved by the platform's per-frame delta and then clamped out of any overlapped static map collision (shallowest-axis push-out, re-checked until clean) — so a platform pushing the player into a wall stops the player at the wall face while the platform keeps moving. Landing on a platform also spawns the landing-dust puff, identical to a ground landing (same shared `MovementSystem.onLanding(...)` helper, random X across the feet, same `5.0`→`10.0` fall-speed scaling), gated by the same one-tile height rule on `PlayerComponent.inAir`/`maxAirHeight` — so a >1-tile fall onto the platform puffs, while riding a platform up or a short hop does not. Jump landings on a platform also squash via `SquashSystem` (same `FeatureFlags.isSquashEnabled()` gate, default off), exactly like ground landings.
5. **Room activation:** Like enemies, a platform only moves while its owning Room is the active one (`roomIndex` vs `RoomState.activeRoomIndex`, assigned from the spawn point at spawn time). The player can still land on a frozen platform, which behaves like a normal static floor.
6. **Level transitions:** Platforms live in the "objects" layer, so `EntityFactory.spawnObjects(...)` re-creates them automatically on every level swap — no `LevelManager` changes needed. Platforms draw at z-layer `6` (above decorations, below the player) and show up in the collision debug overlay like any other entity.

### W. One-Way Platforms & Drop-Through (`MapLoader`, `MovementSystem`, `PlayerInputSystem`, `TouchControlsStage`)
1. **Map authoring:** A one-way platform is an ordinary tile in the **collision layer** whose tile declares a boolean `oneWay=true` custom property (via its tileset, e.g. `assets/maps/world1/drop_platform.tsx`). `MapLoader.buildCollisionRects()` partitions collision-layer tiles as follows: a `hazard=true` tile (see §2.X) is non-solid and goes to `hazardRects`; otherwise a tile whose `solid` property is `false` is skipped entirely; otherwise a tile with `oneWay=true` is **non-solid** for normal physics and goes to the shared `oneWayRects` array; otherwise it's a regular solid and goes to `collisionRects`. See `resources/docs-ai/map-design-for-tiled.md` for the full authoring recipe.
2. **Player top-only; everyone else fully solid:** `MovementSystem` resolves `oneWayRects` differently per entity type. **For the player** it stays a drop-through platform: resolved in the Y phase only, only while falling (`velocity.y <= 0`), and only when the player's feet were at or above the rect's top surface the previous frame (`feetY >= rectTop − 0.5f` epsilon) — the player can **jump up through** a one-way platform from below and **land on top** of it from above, but never collides with it sideways or while rising. **For every other grounded entity** (enemies, popped items) a `oneWay` tile is an ordinary **fully-solid tile, all four sides**: resolved like `collisionRects` in both the X and Y phases, so enemies land on top, are blocked by its sides/underside, and pop-pushed coins rest on it. **Flying enemies pass through one-way tiles entirely** (no gravity → never grounded, so they'd otherwise strand on top of every platform they fly over).
3. **Enemies patrol one-way platforms:** `EnemySystem`'s ledge probe counts `oneWayRects` as ground alongside `collisionRects` (its constructor takes both shared sets), so a grounded enemy walking along a one-way platform doesn't jitter-turn mid-platform; it still turns at the platform's true edge or before a hazard as usual.
4. **Drop-through (`dropWindow`):** Pressing **S** or **DOWN** (keyboard) — or the contextual **`v`** touch button, shown only while the player is grounded on a one-way platform (`player.onDropTile`, set by `MovementSystem` and read by `GameScreen` each frame) — fires `player.dropRequested` for one frame (`PlayerInputSystem`), which `start()`s `player.dropWindow` (~`0.25s`). `PlayerInputSystem` ticks `dropWindow` down every frame, so the window expires ~`0.25s` after the press. While `dropWindow.isActive()`, `MovementSystem` skips the one-way set entirely, so the player falls clean through the platform (into the void or onto whatever is below) instead of being caught on top. Because the window is short and the player falls immediately, the drop feels deliberate rather than sticky; once it expires the player has already fallen below the platform's top surface (so they can't re-stick on the same tile from below) and can land normally on a one-way platform again from above. Any solid ground/floor below is resolved normally once the player falls out of the one-way rect.
5. **Player-only grace:** Holding S/DOWN on solid ground does nothing (no `dropWindow`, no effect) — the key is only meaningful while standing on a one-way platform; like the interact/exit flow, it's a one-shot per-frame flag.
6. **HUD/UI:** The contextual `v` button (`TouchControlsStage.setDropVisible(boolean)`, mirroring the interact up-arrow) renders only while `onDropTile` is true, so the button appears exactly when a drop is available.
7. **Level transitions:** `LevelManager.loadLevel(...)` clears+refills the shared `oneWayRects` in place (same sharing pattern as `collisionRects`/`rooms`, no re-wiring) and resets `dropRequested`/`onDropTile`/`dropWindow` on the surviving player component, so the new level's platforms are live immediately.
8. **Frame-hitch guards:** To survive Android's heavy first-frame hitch (map/GL init can produce a single ~0.3s frame), `GameScreen` clamps the ECS delta to `MAX_FRAME_DELTA = 1/30s` and `MovementSystem` sub-steps the Y-axis collision into `MAX_Y_STEP = 8` world-unit slices. This prevents the player from tunneling through the floor and falling out of the level when a level first loads on a device under load.

### X. Hazard Tiles: Spikes & Lava (`MapLoader`, `HazardSystem`)
1. **Map authoring:** A hazard is an ordinary tile in the **collision layer** whose tile declares a boolean `hazard=true` custom property (e.g. `assets/maps/world1/hazards.tsx`, tile id `0` = spikes, id `1` = lava). `MapLoader.buildCollisionRects()` routes such tiles to the shared `hazardRects` array and **never** makes them solid — the player walks into them freely; only the visual art and the damage check care about them. **Smaller hitbox:** if the tile also has a collision-editor shape drawn in Tiled (rect/polygon/circle on the tile), the damage zone uses one world-space box per shape instead of the full tile — so spike art that only fills part of the tile can have a matching smaller danger area. A hazard tile with no shapes (or a flipped cell) falls back to the full tile.
2. **Damage (`HazardSystem`):** The system holds the `hazardRects` set and checks each one against the player's AABB every frame. On overlap while the player is alive, it calls the shared `PlayerDamageResolver.applyHitWithoutKnockback(...)`: **1 HP** damage, the same `hurtTimer` hit-stun (input lock, hurt pose) and the same `hitInvulnerability` grace (`2.0s`) as any other damage source — but **no knockback**: the player's velocity is untouched, so touching spikes doesn't shove the player off a ledge and standing still in lava only re-damages after the grace window elapses (a ticking drain, not instant death). Because the grace is the shared `hitInvulnerability`, a hazard hit and a nearby enemy/bullet hit still share one combined window (§2.J).
3. **Non-solid:** Hazards never participate in `MovementSystem` AABB resolution (neither `collisionRects` nor `oneWayRects`), so they can be placed anywhere — including mid-air, inside pits, or under one-way platforms — without affecting movement.
4. **Death:** Repeated hazard damage can kill (reaching `0` health triggers the normal `PlayerDeathSystem` game-over flow, §2.P); a dead player is short-circuited out of the overlap check.
5. **Authoring note (scale):** The player's collision box is ≈120×240 px at level-1 scale — taller than a 128×128 tile — so a hazard tile painted as a floor just under the player's feet registers as an overlap the moment the player stands on/over it; when authoring, push hazard art fully under a floor's edge or through the player's body where you want contact, and verify with the SHIFT+D hazard overlay (red).
6. **Level transitions:** `LevelManager.loadLevel(...)` clears+refills the shared `hazardRects` in place like the other map arrays, so new levels' hazards are live immediately.

### Y. Torch Light (`EntityFactory`, `LightComponent`, `LightRenderSystem`)
1. **Cosmetic only:** Torch objects in the object layer spawn a decorative sprite **plus** a `LightComponent` halo drawn with additive blending — a soft warm-orange radial glow centered on the torch flame, gently flickering out of sync per torch (§ the `LightRenderSystem` row in `ashley-ecs.md`). It has **zero gameplay effect**: no occlusion, no darkness, no gameplay-affecting illumination; the world stays fully lit and visible at all times.
2. **Authoring:** Optional `lightRadius` custom property on a `torch` object overrides the default halo radius (`96` world units); omit it for the standard halo. The halo is large (`96` radius, ≈2× the older `48`) and bright (`baseAlpha 0.85` with a warm-white `(1, 0.85, 0.6)` tint) so it reads clearly as torchlight. The light is recreated automatically on every level spawn, and `LevelManager.loadLevel(...)` removes it along with the torch entity on level swaps.

### Z. Secret Walls & Rooms (`MapLoader`, `MeleeAttackSystem`, `LevelManager`)
1. **Map authoring:** A secret wall is an ordinary tile in the **collision layer** whose tile declares a boolean `secret=true` custom property (e.g. `assets/maps/world1/secret_wall.tsx`). In `MapLoader.buildCollisionRects()` precedence (`hazard` > `solid=false` > `oneWay` > solid), a `secret=true` tile is **fully solid**: it lands in the shared `collisionRects` array like any other wall **and** is additionally recorded in the shared `secretRects` array. Unlike a hazard it is *not* passable — the player (and enemies/bullets) are blocked until the wall is actually broken.
2. **Breaking (`MeleeAttackSystem`):** A melee strike (see §2.C) that overlaps a `secretRects` rect and finds no enemy or chest hit first breaks **at most one** wall per swing (`meleeHasHit` is consumed). `breakSecretWall(...)` removes the wall's rect from both the shared `secretRects` and `collisionRects` arrays (so it is passable and no longer drawn in the collision debug overlay from the very next frame), blanks the wall's cell in the collision tile layer (`cell.setTile(null)` — the sprite disappears from the map render), spawns a small smoke puff at the tile center (`ParticleHelper.spawnSmallSmoke`), and plays the wall-break SFX (`AudioManager.playWallBreak()` → `SfxSystem.playWallBreak()`, `sfx/Explosion1.mp3`).
3. **What hides behind:** The level designer seals a small alcove/room on the *other* side of the wall (solid walls/floor/ceiling in the `collision` layer), drops a **`Rooms` rectangle** over it, and places pickups (chest/coins) and optionally enemies inside. Because `RoomState.findRoomIndexContaining(...)` returns the **first** room rectangle containing the player, the secret room rect must sit *before* the enclosing room in the `Rooms` layer so it wins the camera framing — when the player steps into the alcove, `CameraSystem` flips/centers onto the secret room (see `secret_room` in `assets/maps/world1/level_05.tmx` — the full 30-tile room right of room 2, cols 90–119; its west boundary wall at col 89 has the two body-height rows 14–15 replaced with the breakable `secret_wall` tile the player strikes from the last normal room).
4. **Secret rooms hide their existence:** A secret room is *invisible* until revealed. `MapLoader.getSecretRooms()` groups the secret walls with the matching `Rooms` rect and the `secret_hide` tile layer's veil cells covering that rect. The **`secret_hide` layer** (top of the layer stack) is painted with visually-identical rock over the whole secret-room footprint, so from outside the map looks like solid wall; the room's loot/enemy markers (which carry the `secretRoom="<room name>"` object property) are **partitioned out** of the normal `objects`/`enemies` spawn layers into the room's deferred set and do not exist as entities until reveal.
5. **Reveal (`SecretRoomRevealer`):** When `MeleeAttackSystem.breakSecretWall(...)` strikes a wall whose tile declares `secretRoom="<room name>"` (see `MapLoader` — the room name is read from the *tile's own* property, because blanking the cell's tile wipes the cell-level property), it calls `SecretRoomRevealer.reveal(roomName)`: blanks every veil cell over the room (pure visual — collision stays solely in the `collision` layer), spawns the deferred objects/enemies exactly once (`EntityFactory.spawnObjects(...)`, gated by the room's `revealed` flag so breaking two walls of the same room spawns once), and puffs smoke at each veil cell center. The room is now visible, walkable, and lootable.
6. **Level transitions:** `LevelManager.loadLevel(...)` clears+refills the shared `secretRects` in place (same pattern as `collisionRects`/`hazardRects`), pushes the new map's collision tile layer into `MeleeAttackSystem.setCollisionLayer(...)`, and re-seeds the `SecretRoomRevealer` with the new map's rooms + `secret_hide` layer — so a re-entered level's secret walls are solid, breakable, and blanked correctly again, and its hidden rooms re-arm.
7. **Debugging:** An unbroken secret wall shows in the SHIFT+D overlay as a normal yellow solid rect (it is part of `collisionRects`); once broken, the rect is gone from the overlay and the cell renders empty.

### AA. Parallax Scrolling Background (`ParallaxBackgroundSystem`)
A global two-layer parallax skybox draws **behind** every level's Tiled map — the map's own `background` tile layer (dungeon brick walls, pillars, chains) still renders on top of it unchanged. The far layer (`maps/gfx/background/Background_01.png`, factor `GameConstants.PARALLAX_BG_FAR` = `0.25`) scrolls slower than the near layer (`Background_02.png`, factor `PARALLAX_BG_NEAR` = `0.5`), so the world visibly recedes into the distance. Both textures are scaled to cover the effective (zoomed) view and repeated horizontally; positions derive from the shared camera with `position × (1 − factor)`, so the layers track the hybrid flip/scroll camera (§2.N) automatically — static in flip rooms, drifting slower than the world in scroll rooms. It's a code-side renderer (`ParallaxBackgroundSystem`, priority `19`, just before `TiledMapRenderSystem`), **not** a Tiled image layer: libGDX's map renderer ignores Tiled's `parallax`/`repeat` properties, and the tiles are authored once globally rather than per-map. Pure cosmetic — no gameplay effect, no per-level config, survives level swaps untouched (see `resources/docs-ai/ashley-ecs.md`).

### AB. Traps — Acid/Lava Drops & Flame Hazards (`TrapComponent`, `TrapSystem`, `TrapContactSystem`)
1. **Overview:** Two trap types placed via Tiled `type="trap"` object-layer markers: **acid/lava drops** (timer-based falling/rising projectiles) and **flame traps** (pulsing animated hazard zones). Both deal 1 damage on contact, are room-aware (freeze in inactive rooms), and use `PlayerDamageResolver.applyHitWithoutKnockback()` for damage resolution (shared invulnerability grace period prevents frame-by-frame shredding).
2. **Acid/Lava Drop Spawner:** A **visible animated acid tube** at the Tiled marker position (atlas `acid_tube1..4`, 64px sprites rendered at `AcidTubeScale = 0.25 × unitScale`, i.e. exactly one 128px tile). Each interval it plays a one-shot **discharging animation**; only when that animation completes does it release a drop (so the drop visually forms/detaches from the tube). Properties: `direction` (`up`/`down`/`left`/`right`, default `down`), `interval` (seconds between spawns, default 2.0), `speed` (projectile velocity in u/s, default 200), `damage` (default 1). `direction=down` creates acid dripping from ceiling; `direction=up` creates lava geysers from the floor; `direction=left`/`right` creates side-mounted sprayers.
3. **Acid/Lava Drop Projectile:** Spawned **centered on the acid tube** (the tube is a full tile, so each drop's center sits at the marker position + half a tile; no designer-editor offset is used). Released at the end of the tube's discharging animation, the drop first **hangs at the spawn point** (~0.15 s drip-build, so it visibly bulges before releasing), then travels in the configured direction. A **downward (`down`) drip** **accelerates under gravity** (`ACID_DROP_GRAVITY`, 800 u/s²) like a heavy droplet; on landing on a floor/wall it **turns into an `ACID_POOL`** — a ~1 tile wide puddle from the `acid_blob1..7` atlas clip (128×128px sprites, flattened) that plays the **splash animation once** (`SPLASHING` state, `PlayMode.NORMAL`, `0.05s`/frame → ~0.35s splash) and then holds the final splat frame for the remaining pool life — that also deals 1 damage on contact and lingers ~1.5 s before vanishing. **Up/left/right** directions keep constant speed (no gravity) and simply vanish on wall/ceiling/floor contact. All drops are removed on lifetime expiry (5s). Uses the `acid_drop` atlas region (32×32 single frame) rendered at `SpriteConstants.AcidDropScale = 0.25 × unitScale` — half a tile. Collision box is independent of the sprite (4×6 world units before unitScale). The tube/acid visuals come from the game atlas (`gfx/origin-game.atlas`); the old standalone `gfx/acid_drop.png` / `gfx/acid_pool.png` require no longer applies.
4. **Flame Trap:** An animated entity that pulses between small and large size on a cycle. Properties: `direction` (`up`/`down`/`left`/`right`, default `down`), `duration` (flame-on seconds, default 2.0), `cooldown` (off seconds, default 1.5), `pulseSpeed` (oscillation speed, default 2.0). Uses `fire1..10` atlas sprites (256×256) with rotation for side-mounted flames. Collision box scales proportionally with the visual animation — anchored at the source point (ceiling for DOWN, floor for UP, walls for LEFT/RIGHT) and extending outward.
5. **Tiled Object Properties:**

| Property | Type | Default | Used by |
|----------|------|---------|---------|
| `trapType` | string | `"acidDrop"` | Both (`"acidDrop"` / `"flame"`) |
| `direction` | string | `"down"` | Both (`"up"/"down"/"left"/"right"`) |
| `interval` | float | `2.0` | Acid drop spawner |
| `speed` | float | `200` | Acid drop projectile |
| `damage` | int | `1` | Both |
| `duration` | float | `2.0` | Flame (on-time) |
| `cooldown` | float | `1.5` | Flame (off-time) |
| `pulseSpeed` | float | `2.0` | Flame |

6. **Room awareness:** Both trap types check `roomIndex` against `RoomState.activeRoomIndex` each frame. Spawners pause their timers; drops continue moving (they're transient); flames freeze their pulse cycle. Matches existing enemy freeze behavior.
7. **Level transitions:** Trap entities are removed by `LevelManager.loadLevel(...)`'s "remove every non-player entity" cleanup — no special disposal needed.
8. **Damage resolution:** Uses `PlayerDamageResolver.applyHitWithoutKnockback()` (same as `HazardSystem`) — 1 HP damage, no knockback, 2-second invulnerability grace period. The `TrapContactSystem` runs at priority 8 alongside `EnemyContactSystem` and `HazardSystem`.
9. **Debugging:** Trap entity AABBs appear in the SHIFT+D collision debug overlay (lime boxes) like any other `CollisionComponent` entity. Flame traps show dynamically scaling boxes as they pulse.

### AC-Bis. Story Intro (`StoryIntroScreen`)

All user-facing text lives in one place — `com.axehigh.platformer.text.StoryText` (`PROLOGUE_TITLE`, `INTRO_BODY`, `ENTER_BUTTON`) — so narrative can be edited without touching screen code.
3. **Enter action:** Pressing Enter builds a fresh `SaveData` (first catalog level, `triesRemaining = 3`, default stats) and transitions to `GameScreen`. Because `MainMenuScreen` already called `SaveManager.clear()` when the player chose New Game, starting a new game fully resets prior run progress (`completedLevelIds`, `completedWorldIds`, stats, tries).

### AD. UI Skin & Drawables Rule (Mandatory)
- **Never hardcode or guess style/drawable names** (such as `"default-window"`) in Scene2D `Skin.getDrawable(...)` or table backgrounds. 
- Always use drawables verified to exist in the loaded skin/atlas (e.g. `"table"` for container window panels and slot backgrounds, as seen in `InventoryBarStage`). Refer to existing UI code or asset definitions before adding component background styling to avoid runtime `GdxRuntimeException` crashes.

### AE. Vignette Effects & Feature Flags (`VignetteRenderSystem`, `FeatureFlags`)
1. **Overview:** Dual camera-space vignette effects rendered with a dark medieval tint, controlled by independent feature flags.
2. **Cinematic Screen-Edge Vignette:** A subtle radial gradient covering the camera viewport edges (`vignetteCinematicEnabled`, default `true`), giving cinematic dungeon framing.
3. **Player-Centric Torchlight Vignette:** A player-centered torchlight circle/vignette (`vignettePlayerCentricEnabled`, default `true`) that follows the player's world position, enhancing dungeon exploration and unlit room tension.
4. **Configuration & Toggles:** Toggled live in the in-game Pause menu (Gameplay tab) and the Main Menu Preferences screen (Gameplay tab), persisted via `GamePreferences`.
